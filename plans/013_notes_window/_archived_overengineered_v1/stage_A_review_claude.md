# Stage A review (claude)

Reviewed against `plans/013_notes_window/stage_A_shell_and_list.md` and current trunk (`9d1dfb1`). Scope: a standalone NotesWindow shell + sidebar list + read-only center pane; Stage B–E add editing, FTS5, tags, toolbar.

## Verdict

**Rework required — small in scope but blocking.** The plan has two internally-inconsistent claims (the detail-style `TranscriptRow` does not render a title; §5 says the sidebar reuses `.detail`, §5 also says rows show a derived title) and one "first-adopter risk" that is factually wrong (NavigationSplitView is already the `UnifiedWindowView` backbone). Neither makes the direction wrong — a NotesWindow mirroring `UnifiedWindowController`'s hosting pattern is exactly right — but the risk framing and the title/row decision need to land before code starts, otherwise the implementer will ship either a row-with-no-title or a silent divergence into a fork of `TranscriptRow`.

## Critical issues

- **`TranscriptRow(.detail)` does not render a title, period.** Plan §2 "Row reuse" claims "reuse `TranscriptRow` in its existing `.detail` style. It already renders timestamp + 2-line preview" and then says "Derived title = first ~40 chars of text, trimmed". Those two sentences can't both be true: `Sources/PersonalScribeAppKit/Components/TranscriptRow.swift:82-89` hard-codes `displayTitle = ""` for the detail branch, and the detail `body` branch (lines 141-164) never emits a title `Text`. The `.summary` initializer (line 46) is the only one that takes a title. So the plan is either (a) using `.detail` and the sidebar has no title (matches the current Transcriptions-tab convention, no new code needed — but contradicts the plan's own "derived title" sentence and the mockup copy in `ManualNotesVerification.md` line 14 "each sidebar row shows a readable title/preview derived from the transcript text"), or (b) adding a new sidebar initializer/DisplayStyle to `TranscriptRow`, which makes Stage A touch `TranscriptRow` directly — exactly the collision the plan swore it was avoiding (§5 / §10). Pick one and say so; don't ship both claims.

- **NavigationSplitView is not a first adopter — risk framing is wrong.** Plan §10 calls out "SwiftUI `NavigationSplitView` quirks on macOS 14" as if Stage A is introducing the component. It isn't: `Sources/PersonalScribeAppKit/UnifiedWindow/UnifiedWindowView.swift:57` already uses `NavigationSplitView(columnVisibility: .constant(.all))` in production today, and bug #1b (2026-04-21) has already been absorbed via pinned `columnVisibility`. The real risk for Stage A is *diverging* from the pinned-visibility convention — a 2-column split where the sidebar could auto-collapse on narrow widths would regress the same bug #1b class the unified window already fixed. Plan should either reuse the `.constant(.all)` pin or document why NotesWindow deliberately diverges. As written, §10's risk bullet understates this by framing it as generic Sonoma quirks.

## Medium concerns

- **Title-derivation duplication is real — plan doesn't acknowledge the existing helper.** `Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/HomeTab.swift:139-153` exposes `static func title(for entry: TranscriptEntry) -> String` that already does "first non-empty line, trimmed, fallback to date stamp." Plan §2 says "Derived title = first ~40 chars of text, trimmed" — that's a different rule (prefix-by-chars vs. first-line). The 40-char number appears nowhere in `HomeTab.title(for:)` or `TranscriptRow.Formatters.truncate` (which is called by the summary branch with `Layout.titleMaxLength = 60`). Two divergent derivations in two windows is the duplication smell. Either (a) lift `HomeTab.title(for:)` to a shared helper (lives in `Components/` or on `TranscriptEntry`), (b) explicitly reuse `HomeTab.title(for:)` from `NotesWindowViewModel`, or (c) state in writing that NotesWindow's title rule deliberately diverges and why. Plan says none of these.

- **History menu wiring: `ActionID.openTranscriptions` dispatching to a non-Transcriptions window is a footgun.** Plan §4 says "keep the enum case name for now; renaming is a scope cut" and §10 says "leave a `// TODO: rename to .openHistory in #013 Stage B` comment". That's 4 places with mismatched naming: `StatusItemMenuModel.ActionID.openTranscriptions` (case 85), `StatusItemController.openTranscriptions` (field on line 12), `PersonalScribeAppMain.openTranscriptionsTab` (line 202), and the menu item's display title `"History"` (line 192 — already reads "History" in the model). The current code is already in a half-renamed state: the menu title says History, the enum/closure says Transcriptions. Stage A adds a third layer (closure destination is no longer Transcriptions *tab* either). Recommend: bite the rename in Stage A step 1.4 — it's a 4-file mechanical change, smaller than the surface area already touched, and avoids burning a follow-up cycle on grep-and-replace churn. If the implementer chooses to defer, the TODO needs to be in every one of those 4 call sites, not just one.

- **`ManualNotesVerification.md` drift is not just runbook copy; it's a contract drift against the Transcriptions tab.** The runbook (lines 3-30) describes the aspirational full NotesWindow with a Details right panel, search field, and metadata readout — **none of which exists in code today**. Plan §5 says "UPDATE existing runbook … Do not delete the existing rows (they describe later stages)" but those existing rows describe the Transcriptions tab's current behavior *plus* NotesWindow features that don't exist yet. Stage A appending `MV-NOTES-A-01..06` is fine, but the pre-existing rows need a clarifying header ("The following rows track Stages B–E. Stage A only implements MV-NOTES-A-*."), otherwise a dogfood reviewer running this runbook against a Stage-A-only build will hit 4 failing rows and waste a cycle. `ManualVisualVerification.md` line 144 ("'History' is still present (opens the legacy NotesWindow — will be retired in M4)") and line 183 ("Legacy NotesWindow still opens via menu bar → 'History'") are already wrong — there is no legacy NotesWindow in `Sources/` (I grepped; only one stale string reference inside a placeholder alert at `StatusItemController.swift:354`, and a logger line at `PersonalScribeAppMain.swift:309` that actually refers to the new one). Stage A 1.4 should sweep those MV-VISUAL lines too.

- **Transcriptions tab's future is punted to §8b as an "Open Question" — it isn't, it's a Stage A blocker.** The plan ships History → NotesWindow while keeping `AppTab.transcriptions` reachable via the sidebar (row still present in `AppTab.sidebarListCases`). User will end up with two surfaces showing the same data: History-menu-opens-NotesWindow vs. sidebar-Transcriptions-shows-TranscriptionsTab. That's fine for a week of A/B dogfood, but the plan must say that explicitly and commit to a Stage B decision, not defer indefinitely. Recommend §8b be upgraded to "Stage A decision: keep both surfaces, tracked for Stage B go/no-go based on dogfood week. NotesWindow wins if no regressions; Transcriptions tab deleted in Stage B commit 2.X." Otherwise this decays into permanent duplication.

## Minor nits

- **§2 "Stage A MAY reserve the third column as a `nil` detail slot"** — don't. Either ship 2-column now or 3-column with an empty placeholder; "reserved `nil` slot" invites SwiftUI layout noise (empty column still participates in the split's sizing calculus). §8a's "omit the right panel entirely, restructure 2→3 in Stage C" is the right call; delete the §2 "MAY reserve" sentence so there's a single direction.

- **§3 file map is too file-happy for Stage A.** 6 new source files + 2 test files is fine in aggregate, but `NotesSidebarList.swift` + `NotesReadOnlyEditor.swift` as separate files (each likely < 40 LOC in Stage A) is premature. One `NotesWindowView.swift` with private subviews matches how `UnifiedWindowView` is structured today (sidebar + detail as computed properties, not split files). Re-fork if Stage C's right panel drives complexity past the 150-LOC line. Not a blocker, just file-count creep.

- **§6 step 1.2 "duplicate frame-reconcile helper if needed"** — don't duplicate; `UnifiedWindowController.reconciledFrame(for:activeScreenVisibleFrame:)` and `activeScreenVisibleFrame()` are `static`, and `UnifiedWindowController` lives in the same target as `NotesWindowController` would. Stage A can just call `UnifiedWindowController.reconciledFrame(…)` directly. If the plan wants to avoid the cross-controller coupling, extract to a free function (`WindowFrameReconciler.swift`) — but don't duplicate the body. The plan's "duplicate if needed" is the third-worst option after both of those.

- **§6 commit shape — step 1.4 does too much.** Menu routing (source change) + ManualNotes runbook update + ManualVisual runbook cleanup (per the "Medium concerns" #4 above) is three concerns. Split to 1.4 (routing) + 1.5 (runbooks). Stage A becomes 5 commits, well within the plan's own contingency note.

- **§7 "`TranscriptRow` already carries `onDelete: (() -> Void)?` — Stage A passes `nil`"** — correct as a decision, but worth noting that passing `nil` for `onDelete` with `.detail` style *hides the hover-delete affordance entirely* (`TranscriptRow.showsDeleteControl` requires `hasDeleteAction: true`, line 225). So deletion in NotesWindow stays hidden until Stage B wires it back — plan should state that intentional gap for the dogfood reviewer.

## Verification of codex signals

- **Signal 1 (History menu wiring):** **confirmed.** Menu item `id: .openTranscriptions, title: "History"` (`StatusItemMenuModel.swift:191`) dispatches to `openTranscriptions` closure which resolves to `openTranscriptionsTab` → `unifiedWindowControllerHost.showWindow(selecting: .transcriptions)` (`PersonalScribeAppMain.swift:202-204, 231`). Plan's claim that the menu-bar History row routes to the Transcriptions tab is accurate, and the Stage A plan does need to confront the tab-vs-window duplication (see Medium concern #4).

- **Signal 2 (runbook drift):** **confirmed, partial.** `ManualNotesVerification.md` entirely describes an aspirational NotesWindow that does not exist (fresh-install "open History → `<displayName> History` window opens" — currently History opens the unified window's Transcriptions tab). `ManualVisualVerification.md` lines 144 + 183 reference "the legacy NotesWindow" — there is no NotesWindow source tree in `Sources/` (`find ... -type d -name "NotesWindow*"` returns empty). Stage A §5 does mention updating `ManualNotesVerification.md`, but only to append — the existing rows are stale *today* and the drift needs a dedicated sweep.

- **Signal 3 (TranscriptRow reuse contradiction):** **confirmed.** See Critical issue #1 above. Plan §2 reuses `.detail` AND derives a title — these can't both be true against `TranscriptRow.swift:82-89`. Note: codex framed this as "Stage A plan reuses `TranscriptRow` in the detail/center style" — the detail *style* is for sidebar rows per plan §2 and §3, not the center pane. The center pane is a separate `NotesReadOnlyEditor`. But the underlying contradiction codex flagged is real.

- **Signal 4 (title duplication):** **confirmed.** `HomeTab.title(for:)` exists at `HomeTab.swift:139` — first-line-trimmed, date fallback. Plan §2 defines a different rule ("first ~40 chars, trimmed"). Plan does not acknowledge the existing helper. See Medium concern #1.

- **Signal 5 (NavigationSplitView first adopter):** **refuted.** `UnifiedWindowView.swift:57` already uses `NavigationSplitView` in production with the pinned `.constant(.all)` column visibility pattern. Stage A's §10 risk bullet about "macOS 14 quirks" is either vestigial or copied from a pre-M3.1 draft. The actual risk is divergence from the established pin pattern, not adoption of an untested component. See Critical issue #2.

- **Signal 6 (UnifiedWindowController valid mirror):** **confirmed.** No existing NotesWindow source tree; `UnifiedWindowController` (251 lines, canonical NSWindowController + NSHostingController + bug-#041 frame reconciliation + `WindowTint`/`AppTheme` observation) is the natural reference. §2's "mirror UnifiedWindowController verbatim" is the right instinct; the `UnifiedWindowController.reconciledFrame` reuse path (not duplication) is better than what the plan proposes (see Minor nit #3).

## What the plan does well

- **Standalone NSWindowController over a nested tab is the right call.** Reasons given in §2 (Stage E toolbar + right panel want full chrome, mockup clearly isn't a tab-in-tab) are sound. The mirror target is correct.
- **VM + unit tests first, SwiftUI view behind a manual runbook.** `NotesWindowViewModelTests` as the RED-GREEN surface (§5) matches the project's flexible-TDD-for-SwiftUI discipline.
- **Scope cuts in §9 are disciplined** — explicitly excluding search field stub, "+ New Note", related panes, format toolbar is exactly the trimming that keeps Stage A small.
- **#011 collision analysis in §7 is accurate** — #011 is merged on trunk (`bd5ceff`, `30b13f3`, `68ece00` confirmed), Stage A's modified-files list does not overlap with #011's touched files *except* via the `TranscriptRow` reuse decision (which Critical issue #1 forces a fresh decision on).
- **Autosave name chosen distinctly** (§4, §10) — `"PersonalScribeNotesWindow"` avoids the silent-frame-overwrite clash with the unified window's name.
