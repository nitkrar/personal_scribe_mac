# Stage C review (codex)

## Verdict
block pending cross-stage FTS-title-index resolution

Stage C is directionally right about the existing FTS infrastructure and the #043 correction, but it overstates the scope reduction. The current plan leaves the most obvious Stage B+C false negative unresolved: edited note titles are persisted in Stage B but are not searchable in Stage C because `transcripts_fts` still indexes only `text`.

## Critical issues
- FTS5 title-index gap: Stage B makes `title` a first-class persisted field and explicitly punts title FTS to Stage C ([stage_B_editor_and_persist.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_B_editor_and_persist.md#L40), [stage_B_editor_and_persist.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_B_editor_and_persist.md#L183), [stage_B_editor_and_persist.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_B_editor_and_persist.md#L196)). Stage C then re-punts it to “a follow-up” / “a Stage B follow-up” ([stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L37), [stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L156), [stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L173), [stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L182)). Shipping B+C in that state means a user can type the title they just edited and get no hit unless those words also exist in `text`. That is a silent false negative on the first visible NotesWindow search surface, not a harmless tail task. Recommendation: Stage C should own the FTS-title migration and query semantics. If the team insists on zero DDL in C, then Stage B must absorb title indexing into its own migration before C starts, and Stage C’s dependency section must say that explicitly. The current “follow-up” ownership is not acceptable.
- Migration ordering is already conflicting and needs an explicit sequence before execution. Stage B claims `v5_notes_editable_fields` ([stage_B_editor_and_persist.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_B_editor_and_persist.md#L21)), Stage D claims `v5_tags_tables` ([stage_D_tagging.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_D_tagging.md#L41), [stage_D_tagging.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_D_tagging.md#L79)), and the deferred title-FTS work would then need yet another version on top. Recommendation: lock the order as B=`v5_notes_editable_fields`, C=`v6_fts_title_search`, D=`v7_tags_tables`. Stage D already depends on Stage C’s search composition ([stage_D_tagging.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_D_tagging.md#L185)), so bumping D upward is cleaner than letting multiple plans reserve `v5`.
- Prior-art correction verification: the correction is accurate. `a5a841a` is `#043: DatabaseOperationStatus observable plumbing` and `91ea8fa` is its test-only follow-up, not FTS. The current `transcripts_fts` DDL is in `db4ccde` and the current `TranscriptRepository.search(query:)` surface is in `903ffd0`; older legacy FTS prior art exists in `3da4e87` under the removed `SeshatCore` path. The plan should keep citing the storage-layer path, not #043, but this part is now factually sound.

## Medium concerns
- The “zero DDL, zero migration, just an overload + debounce” framing is only partly earned. The current repository search is indeed timestamp-ordered, not BM25-ordered ([TranscriptRepository.swift](/Users/nitinkum/Projects/nitkrar/personal_scribe/Sources/PersonalScribeCore/Database/TranscriptRepository.swift#L145)), so adding ranking is real work. More importantly, Stage C assumes Stage A already built a sidebar search field and a `NotesSidebarViewModel.searchQuery` binding ([stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L5), [stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L39), [stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L155)), but Stage A explicitly says not to render any search `TextField` placeholder and defines a `NotesWindowViewModel` with only `entries` and `selection` ([stage_A_shell_and_list.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_A_shell_and_list.md#L16), [stage_A_shell_and_list.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_A_shell_and_list.md#L28), [stage_A_shell_and_list.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_A_shell_and_list.md#L107)). That means Stage C owns UI and view-model surface changes it currently treats as preexisting.
- The debounce/testing story is under-specified. There is no existing `.debounce(for:)` usage in `Sources/` or `Tests/`, and no scheduler-test infrastructure in the repo or `Package.swift`. The plan’s “prefer a TestScheduler” line ([stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L123)) is not executable as written. It needs to say what abstraction gets injected, or the tests will collapse into wall-clock sleeps. The Swift 6 isolation mitigation is also buried in Risks instead of the Approach: the owner needs to be `@MainActor`, the Combine sink needs an explicit actor hop, and last-write-wins needs a concrete cancellation check before publishing results ([stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L39), [stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L180)).
- The protocol/commit split is not clean. `TranscriptReading` currently has only `recent(limit:)`, `search(query:)`, and `all()` ([TranscriptReader.swift](/Users/nitinkum/Projects/nitkrar/personal_scribe/Sources/PersonalScribeCore/TranscriptReader.swift#L3)). Adding `search(query:limit:)` as a new protocol requirement in commit 3.1 will immediately break existing conformers and test doubles such as [PersonalScribeAppMain.swift](/Users/nitinkum/Projects/nitkrar/personal_scribe/Sources/PersonalScribeAppKit/Composition/PersonalScribeAppMain.swift#L451), [CopyLastTranscriptActionTests.swift](/Users/nitinkum/Projects/nitkrar/personal_scribe/Tests/PersonalScribeAppKitTests/MenuBar/CopyLastTranscriptActionTests.swift#L102), and [TranscriptionsTabViewModelTests.swift](/Users/nitinkum/Projects/nitkrar/personal_scribe/Tests/PersonalScribeAppKitTests/UnifiedWindow/Tabs/TranscriptionsTabViewModelTests.swift#L255). “No callers yet” is false unless the plan adds a default protocol extension or keeps the overload repo-local until the integration commit.
- The tiebreaker choice is internally inconsistent across stages. Stage B says `updated_at` exists for Stage C sort-by-modified behavior ([stage_B_editor_and_persist.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_B_editor_and_persist.md#L35)); Stage C ignores that and uses `timestamp DESC` ([stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L10), [stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L88)). The SQL itself is fine: `ORDER BY bm25(transcripts_fts), ...` is a valid FTS5 ranking shape for MATCHed rows, and empty-query fallback is already guarded before MATCH ([TranscriptRepository.swift](/Users/nitinkum/Projects/nitkrar/personal_scribe/Sources/PersonalScribeCore/Database/TranscriptRepository.swift#L149)). The unresolved question is product semantics: after Stage B lands, should equal-rank recency mean creation time or last edit time? Decide that before coding.
- The sanitizer claims are mostly right but one part is unproven. Signature verified: `makeFTS5Pattern(rawPattern:forTable:)` ([FullTextSearch.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/.build/checkouts/GRDB.swift/Documentation/FullTextSearch.md#L500)). Empty strings and punctuation/operator junk are invalid in GRDB tests ([FTS5PatternTests.swift](/Users/nitinkum/Projects/nitkrar/personal_scribe/.build/checkouts/GRDB.swift/Tests/GRDBTests/FTS5PatternTests.swift#L60)); quoted phrases and suffix-prefix patterns are valid ([FTS5PatternTests.swift](/Users/nitinkum/Projects/nitkrar/personal_scribe/.build/checkouts/GRDB.swift/Tests/GRDBTests/FTS5PatternTests.swift#L25)), and the repo already short-circuits whitespace before calling it ([TranscriptRepository.swift](/Users/nitinkum/Projects/nitkrar/personal_scribe/Sources/PersonalScribeCore/Database/TranscriptRepository.swift#L150)). I did not find evidence for the plan’s specific backslash claim. If backslash behavior matters, add an explicit repo test instead of hand-waving it.

## Minor nits
- “Clear the field to return to the unfiltered RECENT list” is imprecise. Stage A loads `recent(limit: 500)` or similar ([stage_A_shell_and_list.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_A_shell_and_list.md#L18)), but Stage C’s empty-query path hardcodes `reader.recent(limit: 100)` ([stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L39)). Clearing after a search could therefore shrink the list instead of restoring the baseline.
- Commit 3.3 says “delete any placeholder in-memory filter” ([stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L149)), but Stage A explicitly forbids a non-functional search field placeholder ([stage_A_shell_and_list.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_A_shell_and_list.md#L107)). There may be no placeholder filter to delete.
- The proposed punctuation-only repo test uses `"!!!"` / `"..."` ([stage_C_fts5_search.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_C_fts5_search.md#L119)), but the currently proven invalid patterns are things like `"""`, `?!`, `AND`, or a lone quote. Use a known-invalid pattern if you want deterministic TDD instead of guessing which punctuation strings SQLite rejects.

## Scope / approach disagreements
- I would not introduce a public `NotesSidebarSearchModel` as a new state owner. Stage A and Stage B both center on `NotesWindowViewModel` ([stage_A_shell_and_list.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_A_shell_and_list.md#L16), [stage_B_editor_and_persist.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_B_editor_and_persist.md#L85)), and Stage D expects search and tag state on the same model ([stage_D_tagging.md](/Users/nitinkum/Projects/nitkrar/personal_scribe/plans/013_notes_window/stage_D_tagging.md#L187)). A separate helper/service is fine; a second public view-model layer is unnecessary drag on cross-stage composition.
- I would either keep the new ranked search API repo-local until the NotesWindow integration commit, or add a default protocol extension that delegates `search(query:limit:)` to `search(query:)`. Making `TranscriptReading` wider before the callers are ready buys little and complicates the commit split.

## What the plan does well
- The plan correctly identifies that the existing FTS infrastructure is already live in the current database path, and it correctly spots that the current repository search is ordered only by `timestamp DESC`, not by rank ([TranscriptsMigrator.swift](/Users/nitinkum/Projects/nitkrar/personal_scribe/Sources/PersonalScribeCore/Database/Migrations/TranscriptsMigrator.swift#L38), [TranscriptRepository.swift](/Users/nitinkum/Projects/nitkrar/personal_scribe/Sources/PersonalScribeCore/Database/TranscriptRepository.swift#L145)).
- The prior-art correction away from `a5a841a` / `91ea8fa` is materially important and, after verification, correct.
- The repo-level search semantics to test are mostly the right ones: AND, phrase, prefix, limit, and delete-under-active-query are the cases that actually shake out FTS integration bugs. The plan also uses pre-dogfood solo context appropriately for non-core cuts like pagination and saved-search persistence.
