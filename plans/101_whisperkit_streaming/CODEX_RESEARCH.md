# WhisperKit streaming audit for #101

Checked against local `argmax-oss-swift` pin `25c62997041c134b03ca82731ce2f6fd2cae1eb9` / `v1.0.0` (`Package.resolved:5-10`), the existing #101 brief, the #095 notes, and the current batch-only `WhisperKitTranscriberAdapter`.

## A. WhisperKit's streaming API surface

**A1.** `AudioStreamTranscriber` does exist in `v1.0.0`, and it is public: `public actor AudioStreamTranscriber` with a public init that takes `audioEncoder`, `featureExtractor`, `segmentSeeker`, `textDecoder`, `tokenizer`, `audioProcessor`, `decodingOptions`, plus `requiredSegmentsForConfirmation`, `silenceThreshold`, `compressionCheckWindow`, `useVAD`, and `stateChangeCallback` (`Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:20-56`). The default audio shape is 16 kHz mono float samples because `WhisperKit.sampleRate` is `16000`, `AudioProcessor` records into `[Float]`, and the default engine tap resamples to 16 kHz mono with a 100 ms buffer (`Sources/WhisperKit/Core/WhisperKit.swift:38-40`; `Sources/WhisperKit/Core/Audio/AudioProcessor.swift:204-215, 991-1016`). Decode cadence is not per-buffer: the transcriber waits until more than 1 second of new audio has accumulated before running another decode (`Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:130-140`).

**A2.** Output is callback-driven, not `AsyncStream`-driven. The callback type is `@Sendable (oldState, newState) -> Void`, and the state payload is `AudioStreamTranscriber.State` (`Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:6-23`). Input ownership is mixed: `startStreamTranscription()` always requests microphone permission, then calls `audioProcessor.startRecordingLive(...)`, then enters its private `realtimeLoop()` (`Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:76-99`). The seam for custom input is dependency injection of `any AudioProcessing` through either `WhisperKitConfig.audioProcessor` or the `AudioStreamTranscriber` init (`Sources/WhisperKit/Core/Configurations.swift:27-35, 75-120`; `Sources/WhisperKit/Core/WhisperKit.swift:56-60`; `Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:43-56`). So a buffer-fed processor is feasible, but only by emulating the capture API at the `AudioProcessing` layer; there is no public `append(samples:)` API on `AudioStreamTranscriber` itself. One useful seam here: `AudioProcessor.processBuffer(_:)` is public and already appends samples / updates energy / fires the buffer callback (`Sources/WhisperKit/Core/Audio/AudioProcessor.swift:904-920`).

**A3.** Per update, the consumer gets state, not `TranscriptionResult`. The state carries:

`currentText` = current decoder text,  
`confirmedSegments` = stable committed prefix,  
`unconfirmedSegments` = revisable tail,  
plus `lastConfirmedSegmentEndSeconds`, `bufferEnergy`, `unconfirmedText`, and a few counters (`Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:7-17`).

The segment type is `TranscriptionSegment`, which includes `start`, `end`, `text`, `tokens`, and optional `words` and is `Sendable` (`Sources/WhisperKit/Core/Models.swift:574-620`).

## B. EoU / segment-confirmation semantics

**B1.** WhisperKit does **not** expose a true "utterance ended" callback in this streaming API. The only built-in transition is segment confirmation: after each decode, all but the last `requiredSegmentsForConfirmation` segments move into `confirmedSegments`, and the trailing `requiredSegmentsForConfirmation` segments stay unconfirmed (`Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:168-192`). That is a stability frontier, not a silence- or utterance-level boundary. The current #101 brief's sentence "crossing that watermark IS the EoU trigger" is too strong for the current upstream API.

**B2.** `confirmedSegments` is effectively stable once committed. When a newly confirmed prefix exists, WhisperKit advances `lastConfirmedSegmentEndSeconds` to the end of the last confirmed segment (`Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:177-180`), and the next decode sets `DecodingOptions.clipTimestamps = [state.lastConfirmedSegmentEndSeconds]` before running the decode (`Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:195-205`; `Sources/WhisperKit/Core/Configurations.swift:171, 200`). That means future decodes are clipped to start after the confirmed frontier, so already confirmed audio is not re-decoded. I did not find inline docs promising linguistic "utterance" semantics; the code only promises "older than the last N segments" semantics.

**B3.** WhisperKit has built-in silence gating, but not built-in EoU. In streaming, `useVAD` defaults to `true`; when enabled, `AudioStreamTranscriber` calls `AudioProcessor.isVoiceDetected(...)` on recent relative-energy values and skips decode on silent buffers (`Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:142-156`; `Sources/WhisperKit/Core/Audio/AudioProcessor.swift:629-655`). In batch, there is a separate VAD chunking path via `voiceActivityDetector ?? EnergyVAD()` when `decodeOptions.chunkingStrategy == .vad` (`Sources/WhisperKit/Core/WhisperKit.swift:875-911`). Neither path emits an utterance-ended event. The brief's hard-coded "`useVAD: false` because no VAD is needed" is not source-backed; `useVAD` is an implementation choice, not a WhisperKit EoU contract.

## C. Decode semantics: same bug class as whisper.cpp?

**C1.** WhisperKit streaming is **not** fully incremental token streaming. It repeatedly re-transcribes the current accumulated audio buffer, but with a moving cutoff. `transcribeCurrentBuffer()` pulls `audioProcessor.audioSamples`, waits for >1 second of new audio, then calls `transcribeAudioSamples(Array(currentBuffer))`; `transcribeAudioSamples` applies `clipTimestamps` from the last confirmed end before decoding (`Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:126-163, 195-205`). So there is overlap re-decode after the confirmation frontier, but not from the beginning of the session every time.

**C2.** This is therefore **not** the same failure shape as whisper.cpp. Whisper.cpp required us to invent an external stable-segment tracker over overlapping batch windows. Here, WhisperKit already owns the confirmed/unconfirmed split and advances an internal cutoff when segments become confirmed (`Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:168-205`). The unstable part is the unconfirmed tail; the confirmed prefix is already handled inside the library. If the adapter emits only the delta of newly confirmed segments, I do **not** expect the duplicate-lane / parallel-flush bug from whisper.cpp. If the adapter instead treats `currentText` or raw unconfirmed text as append-only cursor output, it will reintroduce revision/jitter problems.

**C3.** There is an explicit cutoff API, but it is internal to the streaming loop. `DecodingOptions` exposes `clipTimestamps` (`Sources/WhisperKit/Core/Configurations.swift:171, 200`), and `AudioStreamTranscriber` sets it from `lastConfirmedSegmentEndSeconds` on every decode (`Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:195-198`). So the cutoff is not just implicit in the arrays; it is a real decode option. Consumers only get direct control of it if they bypass / replace the stock `AudioStreamTranscriber` loop.

## D. Shared-adapter feasibility (matching #100)

**D1.** The shared-adapter plan is feasible. One `WhisperKit` instance owns the reusable runtime graph: `audioProcessor`, `featureExtractor`, `audioEncoder`, `textDecoder`, `segmentSeeker`, plus optional `voiceActivityDetector` (`Sources/WhisperKit/Core/WhisperKit.swift:29-35`). `AudioStreamTranscriber` is then constructed directly from those same pieces (`Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:43-68`). That matches the #100 pattern much more closely than whisper.cpp did.

**D2.** Batch APIs still exist alongside streaming. `WhisperKit.transcribe(audioPath:)` and `WhisperKit.transcribe(audioArray:)` both still return `[TranscriptionResult]` (`Sources/WhisperKit/Core/WhisperKit.swift:823-930`), and our current batch adapter already wraps that into `PersonalScribeCore.TranscriptionResult` via `LiveWhisperKitManager.transcribe(...)` plus `makeTranscriptionResult(...)` (`Sources/PersonalScribeTranscription/Adapters/WhisperKitTranscriberAdapter.swift:423-438, 489-598`). I found no evidence that streaming requires a separate model artifact set or separate runtime configuration.

**D3.** Relevant lifecycle hooks are present but low-level: `WhisperKit.unloadModels()`, `WhisperKit.clearState()`, and `AudioStreamTranscriber.stopStreamTranscription()` (`Sources/WhisperKit/Core/WhisperKit.swift:487-504`; `Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:92-96`). `WhisperKit` and `AudioProcessor` also stop recording in `deinit` (`Sources/WhisperKit/Core/WhisperKit.swift:506-508`; `Sources/WhisperKit/Core/Audio/AudioProcessor.swift:897-899, 1086-1106`). There is no adapter-level idle-release concept upstream; we still need our own wrapper logic like the existing batch adapter's delayed `releaseIdleResources()` path (`Sources/PersonalScribeTranscription/Adapters/WhisperKitTranscriberAdapter.swift:165-187, 245-259`).

## E. Conformance gotchas

**E1.** The runtime objects are mostly **not** `Sendable`: `WhisperKit` is an open class, `WhisperKitConfig` is an open class, `VoiceActivityDetector` is an open class, `AudioProcessing` is a protocol existential backed by classes, and `AudioStreamTranscriber.State` is not annotated `Sendable` (`Sources/WhisperKit/Core/WhisperKit.swift:11`; `Sources/WhisperKit/Core/Configurations.swift:7`; `Sources/WhisperKit/Core/Audio/AudioProcessor.swift:52`; `Sources/WhisperKit/Core/Audio/VoiceActivityDetector.swift:6`; `Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:7-17`). The safe values are `DecodingOptions`, `TranscriptionSegment`, and `TranscriptionProgress`, all of which are `Sendable`, while `TranscriptionResult` is only `@unchecked Sendable` (`Sources/WhisperKit/Core/Configurations.swift:155`; `Sources/WhisperKit/Core/Models.swift:447, 574, 643, 728`). The current `LiveWhisperKitManager` actor is the right containment pattern for Swift 6 strict-concurrency pressure (`Sources/PersonalScribeTranscription/Adapters/WhisperKitTranscriberAdapter.swift:489-598`).

**E2.** Upstream itself is callback-based, so it does not directly recreate our standard `AsyncStream` / `for await` retention trap. `AudioStreamTranscriber` stores `stateChangeCallback` strongly, but its internal async hops use `[weak self]` (`Sources/WhisperKit/Core/Audio/AudioStreamTranscriber.swift:33, 83-86, 200-203`). The pin risk returns when *we* bridge those callbacks into `AsyncThrowingStream<StreamingTranscriptionEvent, Error>` or forward any internal `AsyncStream`; that side should still follow the repo memory: extract streams outside the task body and finish continuations on teardown (`/Users/nitinkum/.claude/projects/-Users-nitinkum-Projects-nitkrar-personal-scribe/memory/project_async_stream_retention.md:7-32`).

**E3.** Local evidence does not support a version-bump recommendation. We are pinned to `argmax-oss-swift` `v1.0.0` in `Package.resolved:5-10`, the checkout `git log` head is the `v1.0.0` release commit, and the local tag list stops at `v1.0.0`. Under this request's local-only constraint, I did not verify a newer upstream release with materially different streaming support.

## Recommendation

Proceed with the **shared-adapter / shared-`WhisperKit`-instance** part of the existing #101 brief, but rewrite the **EoU** section before implementation.

The main correction is this: `confirmedSegments` is a **stable-prefix confirmation boundary**, not a true utterance-ended API. The brief should stop saying that confirmation watermark == EoU, and it should stop treating `useVAD: false` as a WhisperKit requirement. What WhisperKit gives us is stronger than whisper.cpp for dedup, but weaker than Parakeet EOU for explicit boundary semantics.

For the live cursor decision: **leave live cursor ON for WhisperKit streaming**, with one hard constraint: only append the **delta of newly confirmed segments** (or an equivalent stable committed delta), never raw `currentText` / unconfirmed text. On that shape, I do not see whisper.cpp's duplicate-lane bug recurring, because already confirmed audio is clipped out of future decodes. If product semantics require pause-based utterance chunks rather than stable committed chunks, then #101 needs an extra silence/EoU layer; WhisperKit does not supply that out of the box.
