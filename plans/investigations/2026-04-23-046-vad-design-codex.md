## Verdict
The design is directionally right on the big invariant: keep VAD out of `SessionState`/`SessionSnapshot` and reuse the existing stop path, which matches the post-#071 architecture where pill visibility is derived from session state rather than a side channel (`Sources/PersonalScribeCore/SessionState.swift:1-13`, `Sources/PersonalScribeCore/AppStore/AppStore.swift:285-324`, `BACKLOG.md:187-211`). But there is one blocker: if VAD calls `stopIfActive()` inline from `consumeCaptureStream()`, the current stop path re-enters the pipeline and awaits `captureTask?.value` before it publishes `.transcribing`; because `captureTask` is the task currently running `consumeCaptureStream()`, that is a self-await and can leave capture torn down while `sessionState` is still `.recording` (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:248-250`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:324-355`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:512-519`, `Sources/PersonalScribeSession/SessionCoordinator.swift:125-129`).

## State divergence audit
- verified: No new `SessionState` case / snapshot field / pill VM state is the right default. Current state authority lives in `SessionState`, and AppStore derives pill visibility from that state plus model-download progress rather than a second UI holder (`Sources/PersonalScribeCore/SessionState.swift:1-13`, `Sources/PersonalScribeCore/SessionSnapshot.swift:3-25`, `Sources/PersonalScribeCore/AppStore/AppStore.swift:253-364`). `#071` was fixed specifically by deleting the hold side channel and moving hold-ness into session state (`BACKLOG.md:187-199`, `BACKLOG.md:208-211`).
- verified: `hasFired` is a second holder of “auto-stop already consumed” if session lifetime really is capture-loop lifetime. Today there is one `captureTask` per recording, and `consumeCaptureStream()` is the only sample sink (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:248-250`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:316-318`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:512-519`). If the loop exits on first `.speechEnded`, that loop boundary already gives at-most-once; a separate `hasFired` flag repeats the kind of parallel truth `#071` called out (`BACKLOG.md:187-199`).
- verified: Freezing preferences at session start is consistent with existing pipeline behavior. The orchestrator already snapshots `activeContext` at session start and uses that frozen value later during post-processing/output (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:215-216`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:292-293`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:374-380`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:458-460`).
- verified: Bundle-load failure has no existing session-state slot. `SessionSnapshot` cannot represent “VAD unavailable” (`Sources/PersonalScribeCore/SessionSnapshot.swift:3-25`), and AppStore only surfaces session errors/progress (`Sources/PersonalScribeCore/AppStore/AppStore.swift:285-381`). Reusing `SessionState.error(.modelLoadFailure)` would show a user-visible “Model unavailable” pill for an optional feature (`Sources/PersonalScribeCore/Errors.swift:3-12`, `Sources/PersonalScribeCore/AppStore/AppStore.swift:366-381`). The least-bad shape is a provider-local silent disable; that is a hidden capability mismatch with Settings, but not a second session-lifecycle holder if it stays provider-local.

## Race conditions
- verified blocker: Inline auto-stop from the consumer task deadlocks. The call chain would be `consumeCaptureStream()` (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:512-519`) -> coordinator `stopIfActive()` (`Sources/PersonalScribeSession/SessionCoordinator.swift:125-129`) -> `toggleCapture()` (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:84-100`) -> `stopRecordingAndRunPipeline()` (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:324-355`), and that method awaits `captureTask?.value` after `capture.stop()`. When the caller is that same `captureTask` (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:248-250`), the task waits on itself.
- verified: There is also a stop-in-progress window not covered by “late VAD after `.transcribing`”. `stopIfActive()` no-ops only after the visible state changes away from active (`Sources/PersonalScribeSession/SessionCoordinator.swift:125-129`), but the pipeline does not publish `.transcribing` until after `captureTask?.value` and `audioLevelTask?.value` complete (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:324-355`). During that window, a concurrent manual stop and VAD stop still both see `.recording`.
- verified: `@Sendable` is not the problem with `onAutoStopRequested`; liveness is. `SessionCoordinator` strongly owns `pipeline` (`Sources/PersonalScribeSession/SessionCoordinator.swift:13-15`, `Sources/PersonalScribeSession/SessionCoordinator.swift:41-47`, `Sources/PersonalScribeSession/SessionCoordinator.swift:68-74`), so `[weak coordinator]` is the right way to avoid a retain cycle. But if that weak capture is `nil` and the consumer loop returns anyway, `AVAudioCaptureService` treats consumer termination as stop (`Sources/PersonalScribeAudio/AVAudioCaptureService.swift:122-125`, `Sources/PersonalScribeAudio/AVAudioCaptureService.swift:257-270`), which can stop the engine without a matching session-state transition.
- hypothesis: The summary does not specify whether VAD inspects a buffer before or after `bufferedAudio.append(buffer)`. Because the replay stream is built from `bufferedAudio` (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:337-358`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:533-539`), the current buffer should be appended before any early-return auto-stop path or the final chunk can be dropped.

## Protocol shape
- verified: A long-lived provider plus a per-session object is the right conceptual split if the goal is “load CoreML once, keep streaming state per recording”. The codebase already has one long-lived coordinator/pipeline owner and one per-recording `captureTask` (`Sources/PersonalScribeSession/SessionCoordinator.swift:13-15`, `Sources/PersonalScribeSession/SessionCoordinator.swift:41-47`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:248-250`).
- verified: The per-session object does not need to be an actor. `consumeCaptureStream()` is already the sole sample sink (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:512-519`), so a capture-task-local `struct`/`final class` with mutable streaming state is enough. Making `VadSessioning` an actor adds another mutable owner and another suspension point on every buffer without solving a demonstrated sharing problem.
- verified: If you want the smallest seam, keep `VadProviding.makeSession(...)` for injection and make the returned session concrete. Keep a separate `VadSessioning` protocol only if tests genuinely need to stub per-session behavior. The current public pipeline/coordinator contracts do not need to change because stop already exists as `stopIfActive()` and `SessionPipelining` already exposes the active-session controls the coordinator needs (`Sources/PersonalScribeSession/SessionCoordinator.swift:119-131`, `Sources/PersonalScribeSession/Pipeline/Contracts/SessionPipelining.swift:3-19`).

## FluidAudio API verification
- verified: With fresh streaming state, `.speechEnd` requires a prior `.speechStart`. `makeStreamState()` returns `VadStreamState.initial()` (`.build/checkouts/FluidAudio/Sources/FluidAudio/VAD/VadManager+Streaming.swift:5-7`), and `VadStreamState.initial()` defaults `triggered` to `false` (`.build/checkouts/FluidAudio/Sources/FluidAudio/VAD/VadTypes.swift:166-186`).
- verified: The relevant state-machine branches are:

  > `if probability >= threshold { ... if !nextState.triggered { nextState.triggered = true ... event = makeStreamEvent(kind: .speechStart, ...) } }` (`.build/checkouts/FluidAudio/Sources/FluidAudio/VAD/VadManager+Streaming.swift:57-69`)
  >
  > `} else if probability < negativeThreshold && nextState.triggered { ... nextState.triggered = false ... event = makeStreamEvent(kind: .speechEnd, ...) }` (`.build/checkouts/FluidAudio/Sources/FluidAudio/VAD/VadManager+Streaming.swift:70-87`)

- verified caveat: This is not a blanket API guarantee for arbitrary caller-supplied state, because `VadStreamState` has a public initializer that allows `triggered: true` (`.build/checkouts/FluidAudio/Sources/FluidAudio/VAD/VadTypes.swift:172-186`). So the “first-chunk gate for free” argument is valid only if `FluidAudioVadSession` always starts from a fresh stream state.
- verified: The proposed `buffer.samples` feed is compatible with the current capture contract. `PCMBuffer` exposes `samples: [Float]` (`Sources/PersonalScribeCore/PCMBuffer.swift:3-30`), and production capture already yields 16 kHz mono `PCMBuffer` values (`Sources/PersonalScribeAudio/AVAudioCaptureService.swift:5-8`, `Sources/PersonalScribeCore/Storage/AppConfig.swift:3-5`).

## #070 compatibility
- verified current state: Today stop and cancel both tear down capture by calling `capture.stop()` and then awaiting `captureTask?.value` (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:260-266`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:324-330`). In the current implementation, VAD-session lifetime and consumer-loop lifetime are effectively the same thing.
- flagged hypothesis: “No change needed for #070” is not yet verified. `#070` explicitly has not chosen whether pause keeps the capture stream alive or tears it down and re-primes on resume (`BACKLOG.md:639-643`). If pause/resume reuses the same stream, stream-lifetime coupling is fine; if pause/resume creates a new stream, coupling VAD state to stream lifetime resets VAD history across pause boundaries. The design should state that dependency instead of claiming compatibility outright.

## Preference timing
- verified: Session-start snapshotting is consistent with current architecture; I do not see a correctness reason to make VAD preferences live mid-session (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:215-216`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:292-293`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:374-380`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:458-460`).
- verified UX concern: once a Settings slider exists, “disable” or “increase silence threshold” during a live recording will not rescue the current session. That is probably acceptable for Stage A because manual stop already exists as the mode-agnostic escape hatch (`Sources/PersonalScribeSession/SessionCoordinator.swift:119-131`), but it should be documented next to the control and in manual verification.

## Bundled model loading
- verified: Synchronous model load at composition would land on the app’s static composition path. `AppComposition.sessionCoordinator` is built as a static singleton (`Sources/PersonalScribeAppKit/Composition/AppComposition.swift:51-66`), and `SessionCoordinator` / `SessionPipelineOrchestrator` initialization is currently synchronous and light (`Sources/PersonalScribeSession/SessionCoordinator.swift:25-75`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:24-82`).
- verified verdict: I would prefer lazy load on first VAD-enabled session, or a background warm after launch, over synchronous `MLModel(contentsOf:)` at composition. The repo already treats model work as something to defer or background (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:230-239`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:577-595`), and `#012` exists specifically because launch/prepare latency is a known concern (`BACKLOG.md:237-243`). The model is small enough that this is not a blocker, but composition-time load does not match the current performance posture.

## Recommendations
- blocker: Do not invoke `stopIfActive()` inline from the task running `consumeCaptureStream()`. The current stop path awaits `captureTask?.value`; auto-stop must escape that task boundary first or the design recreates the exact “state holders disagree” failure mode it is trying to avoid (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:248-250`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:324-355`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:512-519`).
- strong: Keep the provider/session split if you want one long-lived CoreML owner, but make the per-session VAD state capture-task-local rather than an actor, and drop redundant `hasFired` state (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:512-519`, `BACKLOG.md:187-199`).
- strong: Treat bundle/model-load failure as provider-local “VAD unavailable, recording still works”; do not surface it through `SessionState.error(.modelLoadFailure)` for the recording session (`Sources/PersonalScribeCore/SessionSnapshot.swift:3-25`, `Sources/PersonalScribeCore/AppStore/AppStore.swift:285-381`, `Sources/PersonalScribeCore/Errors.swift:3-12`).
- strong: Mark `#070` compatibility as conditional on the pause/resume implementation choice, not settled fact (`BACKLOG.md:639-643`).
- nice-to-have: Document “VAD settings apply next session” in Settings/manual verification, and preserve the current append-before-stop ordering so the last buffer always reaches transcription (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:337-358`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:512-519`).
