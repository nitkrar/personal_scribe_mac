# #090 — Per-mode descriptor pinning — codex review

**Reviewer:** codex (agent dispatch, 2026-04-29)
**Reviewing:** plans/investigations/2026-04-29-090-descriptor-pinning-claude.md
**Mode:** read-only architectural review.

## Verdict
Ship with revisions: Option A is viable, but the doc currently under-specifies pin-aware validation and misses AppKit/registry surfaces that would otherwise reject or erase valid pins.

## Per-question answers
1. **Option A direct extension:** yes, `descriptorID: String? = nil` is the right level of change. `ProcessorSpec` is already a manually encoded enum, so adding optional keys stays local to one file, and defaulted associated values preserve the existing built-in/preset call sites in `WorkflowMode.dictation` and `Preset.materialize` ([Sources/PersonalScribeCore/WorkflowMode/ProcessorSpec.swift:30-84](Sources/PersonalScribeCore/WorkflowMode/ProcessorSpec.swift), [Sources/PersonalScribeCore/WorkflowMode/WorkflowMode.swift:98-125](Sources/PersonalScribeCore/WorkflowMode/WorkflowMode.swift), [Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/Preset.swift:52-177](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/Preset.swift)). I would not introduce a shared ref struct yet. The revision I do want is that the “voice model” abstraction must cover the ASR leg inside `.diarizedTurns(...)`, because meeting preset uses that case and the detail view always renders a voice-model card ([Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/Preset.swift:114-147](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/Preset.swift), [Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeDetailView.swift:92-109](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeDetailView.swift)); the proposed `voiceModelPinID` limited to `.transcriber`/`.streamingTranscriber` would miss that path ([plans/investigations/2026-04-29-090-descriptor-pinning-claude.md:174-179](plans/investigations/2026-04-29-090-descriptor-pinning-claude.md)).
2. **Diarizer pin schema-yes / UI-no:** I disagree. Backlog scope explicitly names descriptor pinning for `.transcriber`, `.streamingTranscriber`, and the per-turn ASR leg of `.diarizedTurns(...)`, not the diarizer leg ([BACKLOG.md:948-950](BACKLOG.md)). The catalog currently has one diarization descriptor ([Sources/PersonalScribeCore/Models/Selection/BuiltInModelCatalog.swift:249-285](Sources/PersonalScribeCore/Models/Selection/BuiltInModelCatalog.swift)), and the editor currently exposes only an “Identify speakers” toggle, not a diarizer model row ([Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeDetailView.swift:116-129](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeDetailView.swift)). Adding hidden `diarizerDescriptorID` state now creates data the UI cannot inspect, and `withDiarization` currently synthesizes/drops `.diarizedTurns` cases, so preserving a hidden diarizer pin would be easy to get wrong ([Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeRecipeMutators.swift:30-42](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeRecipeMutators.swift)).
3. **Validator signature change:** `registeredDescriptors: [ModelDescriptor]` is workable but not the cleanest injection. Actual validator call sites are `WorkflowModeRegistry.setDefault`, `saveCustom`, `validateCurrentForSessionStart`, and `ModesListViewModel.recomputeValidity`; `RecipeBuilder` does not call the validator today ([Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift:193-204](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift), [Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift:282-327](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift), [Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModesListViewModel.swift:132-143](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModesListViewModel.swift), [Sources/PersonalScribeSession/WorkflowMode/RecipeBuilder.swift:36-110](Sources/PersonalScribeSession/WorkflowMode/RecipeBuilder.swift)). `SessionCoordinator` only calls `registry.validateCurrentForSessionStart(availableKinds:)`, and `AppComposition` already had to weaken `availableKindsProvider` to avoid crossing `ActiveModelService`’s `@MainActor` boundary ([Sources/PersonalScribeSession/SessionCoordinator.swift:321-339](Sources/PersonalScribeSession/SessionCoordinator.swift), [Sources/PersonalScribeAppKit/Composition/AppComposition.swift:80-112](Sources/PersonalScribeAppKit/Composition/AppComposition.swift)). I would either pass a descriptor map/resolver instead of an array, or let `WorkflowModeRegistry` own a descriptor map at init and keep `SessionCoordinator` out of it. Most importantly, pinned specs cannot keep using the current “kind must be in availableKinds” rule or they will still fail when no global active descriptor exists, which is the behavior #090 is supposed to remove ([Sources/PersonalScribeCore/WorkflowMode/WorkflowModeValidator.swift:17-21](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeValidator.swift), [Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift:152-157](Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift), [plans/investigations/2026-04-29-090-descriptor-pinning-claude.md:11-12](plans/investigations/2026-04-29-090-descriptor-pinning-claude.md)).
4. **Mutator “first match” pattern:** first relevant match is sufficient for V1 cardinality, because built-in/preset recipes only carry one voice-model-bearing processor and the existing mutators rewrite in place rather than duplicating processors ([Sources/PersonalScribeCore/WorkflowMode/WorkflowMode.swift:98-125](Sources/PersonalScribeCore/WorkflowMode/WorkflowMode.swift), [Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/Preset.swift:52-177](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/Preset.swift), [Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeRecipeMutators.swift:11-43](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeRecipeMutators.swift)). But the relevant set is broader than Claude wrote: meeting mode’s voice model lives in `.diarizedTurns(..., transcriberKind: .asr)` ([Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/Preset.swift:114-147](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/Preset.swift)), so a mutator that only targets `.transcriber`/`.streamingTranscriber` is incomplete ([plans/investigations/2026-04-29-090-descriptor-pinning-claude.md:174-179](plans/investigations/2026-04-29-090-descriptor-pinning-claude.md)). Pin carry/clear behavior also needs to be explicit: `withDiarization` should preserve the ASR pin into/out of `.diarizedTurns`, while `withRealtime` should clear an incompatible pin when it changes kind from `.asr` to `.streamingASR` or back ([Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeRecipeMutators.swift:11-43](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeRecipeMutators.swift)).
5. **Disabled-descriptor filter:** I agree with using `enabledModels(kind:)` for new picker choices. `ModelDescriptor.isEnabled` is documented as “hide it from live selectors” ([Sources/PersonalScribeCore/Models/Selection/ModelDescriptor.swift:110-112](Sources/PersonalScribeCore/Models/Selection/ModelDescriptor.swift)), `ActiveModelService.enabledModels` enforces that ([Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift:181-186](Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift)), and AI Models tab already uses the same filter ([Sources/PersonalScribeAppKit/Settings/AIModelsTab.swift:22-33](Sources/PersonalScribeAppKit/Settings/AIModelsTab.swift)). The caveat is representation: if a saved mode is pinned to a disabled-but-still-registered descriptor, the picker still needs to resolve/display that current selection from `registeredModels`, or the selection disappears from the control ([Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift:45-47](Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift), [Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift:152-157](Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift), [Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift:181-186](Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift)).
6. **Stale-pin handling:** I agree with “no silent prune at session start,” but save-time throws are only half the story. Registry init currently scrubs stale `defaultModeID`, not invalid custom recipes ([Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift:45-57](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift)), so a previously saved pin can still go stale after a catalog change with no save event. The current architecture will surface that via list validation and session-start revalidation rather than mutating the recipe away ([Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModesListViewModel.swift:132-199](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModesListViewModel.swift), [Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift:322-327](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift), [Sources/PersonalScribeSession/SessionCoordinator.swift:321-339](Sources/PersonalScribeSession/SessionCoordinator.swift)). So I would phrase this as: reject newly edited bad pins on save, and surface already-stored stale pins as invalid; do not silently prune. The comparison point is `ActiveModelService.resolveInitialActiveIDs`, which does prune stale global active IDs because those are preferences, not authored recipes ([Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift:420-447](Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift)).
7. **TDD order:** the logical sequence is mostly right, but there are hidden compile dependencies. Validator tests that mention `descriptorID` cannot compile until `ProcessorSpec` grows those associated values ([Sources/PersonalScribeCore/WorkflowMode/ProcessorSpec.swift:25-84](Sources/PersonalScribeCore/WorkflowMode/ProcessorSpec.swift)), and new `WorkflowModeValidationError` cases will immediately break `ModesListViewModel.message(for:)` exhaustiveness ([Sources/PersonalScribeCore/WorkflowMode/WorkflowModeValidationError.swift:5-24](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeValidationError.swift), [Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModesListViewModel.swift:171-199](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModesListViewModel.swift)). I would start with minimal schema/signature scaffolding plus compile-only caller updates, then drive validator behavior. I would also add an early validator test for “pinned spec validates without a globally active descriptor,” because the current `availableKinds` rule is exactly what #090 is trying to bypass ([Sources/PersonalScribeCore/WorkflowMode/WorkflowModeValidator.swift:17-21](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeValidator.swift), [Sources/PersonalScribeCore/WorkflowMode/WorkflowModeValidator.swift:33-91](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeValidator.swift), [plans/investigations/2026-04-29-090-descriptor-pinning-claude.md:11-12](plans/investigations/2026-04-29-090-descriptor-pinning-claude.md)).
8. **Anything missed / extra consumers:** the missed `ProcessorSpec`/validation surfaces are `WorkflowModeRegistry` (three validator call sites), `ModesListViewModel.recomputeValidity` plus its exhaustive error mapping, `ModeDetailViewModel`’s case inspection, and `ModeRecipeMutators`’ case-rewriting logic ([Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift:193-204](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift), [Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift:282-327](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift), [Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModesListViewModel.swift:132-199](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModesListViewModel.swift), [Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeDetailViewModel.swift:27-32](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeDetailViewModel.swift), [Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeRecipeMutators.swift:11-43](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeRecipeMutators.swift)). The `SessionPipelineOrchestrator` grep hits are downstream `BoundProcessor` consumers, not `ProcessorSpec` consumers, so they do not need descriptor-pin plumbing as long as `RecipeBuilder` binds the right adapters first ([Sources/PersonalScribeSession/WorkflowMode/BoundRecipe.swift:40-47](Sources/PersonalScribeSession/WorkflowMode/BoundRecipe.swift), [Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:184-195](Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift), [Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:633-652](Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift), [Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:1081-1092](Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift)).

## Things claude missed
- Pinned processors must bypass the current `availableKinds` late-bind requirement when `descriptorID` is set; otherwise a pinned mode still fails validation whenever no global active descriptor exists for that kind ([Sources/PersonalScribeCore/WorkflowMode/WorkflowModeValidator.swift:17-21](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeValidator.swift), [Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift:152-157](Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift), [plans/investigations/2026-04-29-090-descriptor-pinning-claude.md:11-12](plans/investigations/2026-04-29-090-descriptor-pinning-claude.md)).
- Meeting mode uses `.diarizedTurns`, so the voice-model getter/mutator must operate on that case’s transcriber leg, not only `.transcriber`/`.streamingTranscriber` ([Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/Preset.swift:114-147](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/Preset.swift), [Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeDetailView.swift:92-109](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeDetailView.swift), [plans/investigations/2026-04-29-090-descriptor-pinning-claude.md:174-179](plans/investigations/2026-04-29-090-descriptor-pinning-claude.md)).
- `ModesListViewModel` is in scope: it directly calls `WorkflowModeValidator.validate` and exhaustively maps `WorkflowModeValidationError`, so new error cases and pin semantics require changes there ([Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModesListViewModel.swift:132-199](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModesListViewModel.swift)).
- `WorkflowModeRegistry` is in scope: it owns three validator call sites and currently has no descriptor-registry dependency, so any signature change ripples through that abstraction, not just `SessionCoordinator` ([Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift:18-21](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift), [Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift:193-204](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift), [Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift:282-327](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift)).
- The concrete manual-verification runbook file already exists: `Tests/ManualVerifications/ManualModesVerification.md`; this is not TBD ([Tests/ManualVerifications/ManualModesVerification.md:1-100](Tests/ManualVerifications/ManualModesVerification.md)).
- The current production registry/session wiring already weakens validation to “all enabled kinds” because of actor-isolation constraints, so “validator throws at save time” is not as immediate or strict as the doc implies ([Sources/PersonalScribeAppKit/Composition/AppComposition.swift:80-112](Sources/PersonalScribeAppKit/Composition/AppComposition.swift), [Sources/PersonalScribeAppKit/Composition/AppComposition.swift:120-139](Sources/PersonalScribeAppKit/Composition/AppComposition.swift)).

## Risks / unknowns
- If the picker uses `enabledModels` but runtime validation accepts any registered descriptor, disabled descriptors become representable in persisted data but not selectable in UI unless the selected-value rendering handles that case explicitly ([Sources/PersonalScribeCore/Models/Selection/ModelDescriptor.swift:110-112](Sources/PersonalScribeCore/Models/Selection/ModelDescriptor.swift), [Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift:181-186](Sources/PersonalScribeSession/Models/Selection/ActiveModelService.swift)).
- If `withRealtime` / `withDiarization` do not intentionally carry or clear pins, toggling those switches can silently drop a user’s pin or leave an incompatible `descriptorID` behind ([Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeRecipeMutators.swift:11-43](Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/Modes/ModeRecipeMutators.swift)).
- Any change to `WorkflowModeRegistry` init for descriptor injection touches non-MainActor composition code that already had to compromise on `availableKindsProvider`; that boundary is where a “clean” validator signature is most likely to get awkward ([Sources/PersonalScribeAppKit/Composition/AppComposition.swift:80-112](Sources/PersonalScribeAppKit/Composition/AppComposition.swift)).
- `RecipeBuilder` and the validator can drift unless they enforce the same pin rules. Today the builder has its own runtime error surface and does not call the validator ([Sources/PersonalScribeSession/WorkflowMode/RecipeBuilder.swift:105-114](Sources/PersonalScribeSession/WorkflowMode/RecipeBuilder.swift), [Sources/PersonalScribeCore/WorkflowMode/WorkflowModeValidator.swift:33-101](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeValidator.swift)).
- Persisted stale pins will remain in `workflow-modes.json` until the user edits/deletes the mode; current registry init does not migrate invalid recipes, only stale `defaultModeID` ([Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift:45-57](Sources/PersonalScribeCore/WorkflowMode/WorkflowModeRegistry.swift)).
