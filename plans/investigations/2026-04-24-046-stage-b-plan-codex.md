## Verdict
Mostly sound, but not ready to execute exactly as written. Two blockers stand out: the proposed `vadAutoStopJustFired: Bool` latch is the wrong shape for a read-only `SessionSnapshot`, and grace resolution needs a single actor-owned token/state so timer, manual-fire, cancel, and error paths cannot double-stop or leave stale UI state (`Sources/PersonalScribeCore/SessionSnapshot.swift:3-25`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:225-235`, `Sources/PersonalScribeSession/SessionCoordinator.swift:204-209`, `plans/046_vad_stage_b/PLAN.md:77-81`, `plans/046_vad_stage_b/PLAN.md:93-117`).

## Question 1 (vadAutoStopJustFired latch)
- Verified against source: `SessionSnapshot` is an `Equatable` value type, and `SessionPipelineOrchestrator.publish` only yields when the whole snapshot changes (`Sources/PersonalScribeCore/SessionSnapshot.swift:3-25`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:225-235`). Consumers only get read access through `snapshot()` / `snapshotStream()`; there is no existing consumer mutation path back into the pipeline (`Sources/PersonalScribeSession/SessionCoordinator.swift:204-209`, `Sources/PersonalScribeAppKit/Overlay/PillOverlayController.swift:143-176`).
- Verified against source: `lastCompletedResult` is durable state, not a fire-once latch. The pipeline writes it on `.completed`, `SessionCoordinator.lastResult()` just reads it back, and `AppStore` copies it into `lastTranscriptionResult` when it sees the `.completed` transition (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:463-469`, `Sources/PersonalScribeSession/SessionCoordinator.swift:237-239`, `Sources/PersonalScribeCore/AppStore/AppStore.swift:132-141`).
- Reasoned from plan: `Bool` + “consumer clears on read” is the wrong shape. The consumer cannot clear it, and if the producer leaves it `true`, every later publish will continue to surface it. I would use a producer-owned monotonic token/timestamp on the snapshot instead of a sticky bool, or a separate routed event stream if you are willing to add API surface. I would not ship the proposed bool latch (`plans/046_vad_stage_b/PLAN.md:77-81`).

## Question 2 (speechResumed via Silero)
- Verified against source: the Silero streaming state machine does emit `speechStart` when `triggered` flips `false -> true`, and `speechEnd` resets `triggered` back to `false` (`.build/checkouts/FluidAudio/Sources/FluidAudio/VAD/VadManager+Streaming.swift:57-87`). `FluidAudioVadSession` starts each recording from `VadStreamState.initial()`, so that transition sequence is the one this code actually uses (`Sources/PersonalScribeVAD/FluidAudioVadSession.swift:21-27`).
- Verified against source: the current seam collapses all raw VAD output down to `.speechEnded`, so there is no way to observe resumed speech without extending `VadEvent` and `FluidAudioVadSession` (`Sources/PersonalScribeVAD/VadMonitoring.swift:3-9`, `Sources/PersonalScribeVAD/FluidAudioVadSession.swift:37-49`).
- Verified against source: the current orchestrator loop stops ingesting VAD entirely after the first `.speechEnded` because `vadAlreadyFired` gates `handle.ingest(...)` (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:563-581`). Stage B therefore needs a richer local phase than “already fired” if it wants `.speechResumed` to cancel grace.
- Reasoned from plan: mapping a post-end `speechStart` to `.speechResumed` is viable and clearly better than waiting for a second `.speechEnded`. The fallback in the plan is unnecessary if you replace `vadAlreadyFired` with a local state such as `idle / gracePending / resolved` and keep ingesting while grace is pending (`plans/046_vad_stage_b/PLAN.md:119-121`).

## Question 3 (link-to-Settings)
- Verified against source: there is already a clean top-level Settings-open path. `PersonalScribeAppMain` builds `openSettingsTab` as `unifiedWindowControllerHost.showWindow(selecting: .settings)`, and `⌘,` uses that same host path (`Sources/PersonalScribeAppKit/Composition/PersonalScribeAppMain.swift:206-208`, `Sources/PersonalScribeAppKit/Composition/PersonalScribeAppMain.swift:305-310`). `StatusItemController` just calls the injected `openSettings` closure (`Sources/PersonalScribeAppKit/MenuBar/StatusItemController.swift:11-16`, `Sources/PersonalScribeAppKit/MenuBar/StatusItemController.swift:141-142`).
- Verified against source: there is no existing “Settings sub-tab” routing API. `UnifiedWindowModel` only stores `activeTab`, `UnifiedWindowController.showWindow(selecting:)` only accepts `AppTab`, and `SettingsTab` keeps `selectedSubTab` as private local `@State` (`Sources/PersonalScribeAppKit/UnifiedWindow/UnifiedWindowModel.swift:3-20`, `Sources/PersonalScribeAppKit/UnifiedWindow/UnifiedWindowController.swift:154-159`, `Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/SettingsTab.swift:5-30`). I also did not find an existing settings-focus notification pattern; `UnifiedWindowController` currently only observes `UserDefaults.didChangeNotification` for theme/tint (`Sources/PersonalScribeAppKit/UnifiedWindow/UnifiedWindowController.swift:101-109`).
- Reasoned from plan: if minimum ship is “open Settings” only, reuse the existing closure and skip new notification plumbing. If the link must guarantee General when Settings is already open on another sub-tab, a typed navigation API is cleaner than `Notification.Name.requestVadSettingsFocus`: promote settings destination into the window model/host instead of adding a new side channel (`plans/046_vad_stage_b/PLAN.md:168-170`).

## Question 4 (grace-timer race)
- Verified against source: coordinator stop is actor-serialized and already documented as idempotent vs concurrent manual/VAD stops (`Sources/PersonalScribeSession/SessionCoordinator.swift:92-100`, `Sources/PersonalScribeSession/SessionCoordinator.swift:151-158`).
- Reasoned from plan: the grace design is not race-free as written. `graceTimerTask = Task { sleep; await handler() }` runs outside the orchestrator actor, so cancelling that task is only cooperative. If the timer wakes and passes its cancellation check before manual fire/cancel lands, both paths can still invoke the handler (`plans/046_vad_stage_b/PLAN.md:93-117`, `plans/046_vad_stage_b/PLAN.md:207-208`).
- Reasoned from plan: you do not need extra locks, but you do need a generation/token check owned by the orchestrator actor. The timer should re-enter the actor and ask “is grace `<id>` still pending?” before firing. Manual stop, Esc-cancel, timer-elapsed, and error teardown should all resolve through that same actor-isolated method.
- Verified against source: the current UI entry points only own `SessionCoordinator`, not `SessionPipelineOrchestrator`, so the plan’s public orchestrator methods are not directly callable from `PersonalScribeAppMain`/hotkey code without coordinator pass-throughs (`Sources/PersonalScribeAppKit/Composition/PersonalScribeAppMain.swift:12-13`, `Sources/PersonalScribeAppKit/Composition/PersonalScribeAppMain.swift:131-140`, `Sources/PersonalScribeAppKit/Composition/AppComposition.swift:120-135`).
- Reasoned from plan: the specific “manual hotkey during grace” sequence in the plan should not be `fireVadGraceImmediatelyIfPending()` and then `stopIfActive()`. Pick one path. If `fire...` already invokes the stop handler, the extra `stopIfActive()` is redundant and makes the race surface larger (`plans/046_vad_stage_b/PLAN.md:208`, `plans/046_vad_stage_b/PLAN.md:274`).

## Question 5 (error priority)
- Verified against source: a top-level `.error` branch in the driver is enough to suppress warning/notification. `SessionState` is an exclusive enum, so there is no `.transcribing + .error` combined state, and `AppStoreSnapshot.sessionState` preserves `.error` as `.error` (`Sources/PersonalScribeCore/SessionState.swift:1-12`, `Sources/PersonalScribeCore/AppStore/AppStoreSnapshot.swift:27-33`).
- Verified against source: `PillOverlayController` recomputes the card state from every AppStore snapshot and will either update or hide the card based on the driver result (`Sources/PersonalScribeAppKit/Overlay/PillOverlayController.swift:155-176`). `AppStore` updates `snapshot.session` before running its error-path pill logic, so the driver will see the latest session state (`Sources/PersonalScribeCore/AppStore/AppStore.swift:118-124`, `Sources/PersonalScribeCore/AppStore/AppStore.swift:145-153`).
- Verified against source: current error UX lives in pill visibility, not in the response card (`Sources/PersonalScribeCore/AppStore/AppStore.swift:145-153`). So “error overrides warning/notification” is satisfied by a top short-circuit; the real leak risk is stale grace state after the error clears, not a simultaneous `.transcribing + .error` state.

## Question 6 (SwiftUI animation)
- Verified against source: I could not locate an existing collapsible Settings-card pattern to copy. The Settings surface is a plain `ScrollView` containing a `VStack` of `SettingsCard`s, and `SettingsCard` itself is just a `VStack` with padding/background (`Sources/PersonalScribeAppKit/Settings/SettingsLayout.swift:28-49`, `Sources/PersonalScribeAppKit/Settings/SettingsLayout.swift:86-128`).
- Verified against source: the only nearby `.animation(..., value:)` precedent I found is the pill/cancel-card crossfade, which is explicitly scoped to one visibility transition and is not analogous to animating card-height changes in a scrolling settings form (`Sources/PersonalScribeAppKit/Overlay/PillOverlayView.swift:194-200`, `Sources/PersonalScribeAppKit/Overlay/PillOverlayPresenter.swift:372-378`).
- Reasoned from plan: `.animation(.default, value: viewModel.vadAutoStopEnabled)` is not obviously wrong, but it is unproven in this stack and may relayout sibling cards/scroll position in a way that feels sloppy. I would treat it as optional polish, not a load-bearing part of the plan, and manual-verify it specifically (`plans/046_vad_stage_b/PLAN.md:181-200`).

## Question 7 (error teardown order)
- Verified against source: current `handleStageFailure` only records the failure and publishes `.error`; it does not clear any other session fields (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:605-611`).
- Verified against source: `publish` yields immediately on any snapshot inequality (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:225-235`). If Stage B implements `cancelVadGraceIfPending()` as a separate publishing helper and then calls `handleStageFailure`, observers will see an intermediate non-error snapshot before the error snapshot.
- Reasoned from plan: the error path should clear grace state and publish `.error` in the same actor turn, ideally the same `publish` mutation, not as two back-to-back publishes. That avoids zombie warning state and avoids a transient `.recording without warning` snapshot on the way to `.error` (`plans/046_vad_stage_b/PLAN.md:307-310`).
- Verified against source: current start/cancel helpers do not reset any future VAD UI fields because those fields do not exist yet (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:274-279`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:305-310`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:327-332`). Stage B should clear grace/notification state on next session start and cancel paths too, since the plan says notification dismisses on next session start (`plans/046_vad_stage_b/PLAN.md:41-43`).

## Additional findings
- Verified against source: the #071 lesson applies here. The risky part is not “two VAD-related fields exist,” but that the plan makes `vadAutoStopGraceDeadline` producer-owned while `vadAutoStopJustFired` is described as consumer-cleared. That is split authority over one interaction, which is the same class of drift #071 removed (`BACKLOG.md:183-199`, `BACKLOG.md:207-211`, `plans/046_vad_stage_b/PLAN.md:77-81`).
- Verified against source: Stage A’s key invariant is preserved only if every stop still escapes the capture consumer task. Current source and tests explicitly guard against self-await deadlock when VAD requests stop (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:357-367`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:576-581`, `Tests/PersonalScribeSessionTests/Pipeline/VadOrchestratorIntegrationTests.swift:68-102`). `fireVadGraceImmediatelyIfPending()` must preserve that invariant too.
- Verified against source: the plan’s file mapping is off in a few load-bearing places. The recording-status driver is consumed in `PillOverlayController`, not `PersonalScribeAppMain` (`Sources/PersonalScribeAppKit/Overlay/PillOverlayController.swift:149-176`, `plans/046_vad_stage_b/PLAN.md:248-253`). The existing Settings-open closure lives in `PersonalScribeAppMain`, not `AppComposition` (`Sources/PersonalScribeAppKit/Composition/PersonalScribeAppMain.swift:206-208`, `Sources/PersonalScribeAppKit/Composition/PersonalScribeAppMain.swift:305-310`, `Sources/PersonalScribeAppKit/Composition/AppComposition.swift:104-138`). ## Parallel-execution risks
- Chunk B / Chunk E are not fully independent. The app/hotkey layer only knows `SessionCoordinator`, so any new grace-control API used by Esc/hotkey likely requires coordinator pass-through methods, not just orchestrator edits (`Sources/PersonalScribeSession/SessionCoordinator.swift:151-158`, `Sources/PersonalScribeAppKit/Composition/PersonalScribeAppMain.swift:131-140`, `Sources/PersonalScribeAppKit/Composition/AppComposition.swift:120-135`).
- Chunk C / Chunk E overlap more than the plan suggests. Response-card link support changes `ResponseCardPresenting`, `LiveResponseCardBuilder`, `PillOverlayPresenter`, `PillOverlayController`, and `ResponseCardView`; the plan currently splits those ownership lines across C and E and points one of them at the wrong file (`Sources/PersonalScribeAppKit/Overlay/ResponseCard.swift:5-33`, `Sources/PersonalScribeAppKit/Overlay/PillOverlayPresenter.swift:488-532`, `Sources/PersonalScribeAppKit/Overlay/PillOverlayController.swift:155-176`, `Sources/PersonalScribeAppKit/Components/ResponseCardView.swift:15-75`, `plans/046_vad_stage_b/PLAN.md:248-274`).
- Chunk D / Chunk E also overlap unless the link only reuses the existing “open Settings” closure. Guaranteeing General-tab focus requires work in the unified-window routing layer (`Sources/PersonalScribeAppKit/UnifiedWindow/UnifiedWindowModel.swift:12-20`, `Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/SettingsTab.swift:5-30`, `Sources/PersonalScribeAppKit/Composition/PersonalScribeAppMain.swift:206-208`).
- Safer split: keep Chunk D purely settings preferences/UI; keep Chunk B as orchestrator + coordinator grace API + VAD events; keep Chunk C as response-card model/render/presenter integration; keep Chunk E only for unified-window deep-link routing plus manual-verification/runbook work.

## Recommendations
- blocker: replace `vadAutoStopJustFired: Bool` with a producer-owned fire token/timestamp or a dedicated routed event stream. Do not rely on a consumer-clears latch in `SessionSnapshot` (`Sources/PersonalScribeCore/SessionSnapshot.swift:3-25`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:225-235`, `Sources/PersonalScribeCore/AppStore/AppStore.swift:132-141`).
- blocker: make grace resolution actor-owned and tokenized. Timer elapsed, manual fire, Esc cancel, and error teardown should all re-enter one resolver that decides whether the stop handler runs. Remove the planned “fire, then `stopIfActive()` anyway” sequence (`plans/046_vad_stage_b/PLAN.md:93-117`, `plans/046_vad_stage_b/PLAN.md:207-208`, `plans/046_vad_stage_b/PLAN.md:274`).
- strong: extend `VadEvent` with resumed speech and keep ingesting while grace is pending; the current `vadAlreadyFired` bool must become a richer local phase (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:563-581`, `Sources/PersonalScribeVAD/VadMonitoring.swift:3-9`, `.build/checkouts/FluidAudio/Sources/FluidAudio/VAD/VadManager+Streaming.swift:57-87`).
- strong: if the link must always land on Settings → General even when the window is already open elsewhere, lift settings destination into the unified-window model/host instead of introducing a notification side channel. If “open Settings” is sufficient, reuse the existing closure and skip the extra plumbing (`Sources/PersonalScribeAppKit/Composition/PersonalScribeAppMain.swift:206-208`, `Sources/PersonalScribeAppKit/UnifiedWindow/Tabs/SettingsTab.swift:5-30`, `Sources/PersonalScribeAppKit/UnifiedWindow/UnifiedWindowModel.swift:12-20`).
- strong: clear grace/notification state in the same publish as `.error`, and also clear it on new-session start/cancel. Do not leave cleanup to observers (`Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:225-235`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:274-279`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:305-310`, `Sources/PersonalScribeSession/Pipeline/Orchestrator/SessionPipelineOrchestrator.swift:605-611`).
- strong: recut the parallel chunks around the real ownership boundaries before dispatching subagents. In particular, move response-card/link wiring into the files that already own it (`PillOverlayController`, `PillOverlayPresenter`, `ResponseCard`, `ResponseCardView`, `PersonalScribeAppMain`) and budget coordinator pass-throughs for grace actions (`Sources/PersonalScribeAppKit/Overlay/PillOverlayController.swift:149-176`, `Sources/PersonalScribeAppKit/Overlay/PillOverlayPresenter.swift:488-532`, `Sources/PersonalScribeAppKit/Components/ResponseCardView.swift:15-75`, `Sources/PersonalScribeAppKit/Composition/PersonalScribeAppMain.swift:131-140`).
- nice-to-have: treat `.animation(.default, value:)` as optional polish. Ship the collapsed layout first, then keep or drop the animation based on manual verification in the real `ScrollView` stack (`Sources/PersonalScribeAppKit/Settings/SettingsLayout.swift:28-49`, `plans/046_vad_stage_b/PLAN.md:181-200`).
