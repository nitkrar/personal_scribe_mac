# 2026-04-26 Security Audit — Lane 4 Persistence (Codex retry)

## 1. Threat-model framing
This lane persists plaintext transcript history in SQLite under the app-support base directory, has a prepared plaintext JSON sidecar for workflow-mode metadata at the base-directory root, and performs filesystem migration/probe writes in the same area. Under the stated threat model, every on-disk copy matters: the main risks are backup/indexing of the persistence root, SQLite sibling files that escape explicit permission hardening, stale legacy directories that remain on disk, and any raw-audio sidecars that outlive their owning transcript rows. I found no app-layer encryption in the audited code, so effective protection is limited to filesystem permissions plus any host-level full-disk encryption outside this repo.

## 3. Findings
- high, Sources/PersonalScribeCore/Storage/AppConfig.swift:109, Sources/PersonalScribeCore/Storage/AppStorageLocator.swift:41, Sources/PersonalScribeCore/Database/AppDatabase.swift:41: The default persistence root is `~/Library/Application Support/personal_scribe`, the code eagerly creates that base directory and its managed subdirectories, and transcript data is then written under `<base>/recordings/transcripts.sqlite`; the required grep found no `isExcludedFromBackup`, `.metadata_never_index`, or `setResourceValues` usage anywhere under `Sources/`. Why: plaintext transcript text, timestamps, and duration metadata (`TranscriptStore.swift:4`, `TranscriptsMigrator.swift:26`) and any future root-level sidecars are therefore backup/index eligible by default, which is directly against this audit's leak model. Mitigation: set `URLResourceValues.isExcludedFromBackup = true` on the base directory and persisted files, create a `.metadata_never_index` marker in the base directory during storage bootstrap, and add regression coverage so new persistence paths inherit the same policy.
- medium, Sources/PersonalScribeCore/Database/AppDatabase.swift:57, Sources/PersonalScribeCore/Database/AppDatabase.swift:192: SQLite is opened with bare `DatabaseQueue(path:)`, and the code only forces `0600` on `transcripts.sqlite` itself after open/migrate. Why: the journal mode is not pinned here, so rollback-journal or WAL siblings in `<base>/recordings/` are possible, and those sibling files can contain the same transcript text/FTS content while inheriting default permissions because only the main database file is chmodded. I saw no app-layer encryption and no sibling cleanup policy beyond whatever SQLite does on a clean shutdown. Mitigation: explicitly configure the journal strategy, harden all SQLite artifacts (`transcripts.sqlite`, `-journal`, `-wal`, `-shm`) to `0600`, and remove unexpected stale siblings during startup or controlled shutdown.
- medium, Sources/PersonalScribeCore/BaseDirectoryMigrator.swift:88, Sources/PersonalScribeAppKit/Composition/AppComposition.swift:20: The one-shot legacy `~/Library/Application Support/Seshat/` to `~/Library/Application Support/personal_scribe/` migrator is implemented with `moveItem`, which would remove the source path if it ever ran, but I found no callsite under `Sources/`. Why: installs with old `Seshat` data can retain a second on-disk copy indefinitely, so legacy transcripts and other persisted material remain as an untracked leak surface even though current startup immediately resolves the new base directory. Mitigation: invoke `migrateFromLegacyBrandDirectoryIfNeeded()` during startup before opening current persistence, then verify that the old path is gone and log or surface a failure if cleanup did not complete.
- low, Sources/PersonalScribeSession/WorkflowMode/WorkflowModeStore.swift:72, Sources/PersonalScribeSession/WorkflowMode/WorkflowModeStore.swift:82, Sources/PersonalScribeCore/WorkflowMode/WorkflowModeDocument.swift:5, Sources/PersonalScribeCore/BaseDirectoryMigrator.swift:123: `WorkflowModeStore` writes plaintext `workflow-modes.json` at `<base>/workflow-modes.json` with `Data.write(..., .atomic)` and no explicit permissions, and `BaseDirectoryMigrator.migrate(to:)` only moves `ManagedDirectory` subdirectories, so this root-level sidecar would not move to a new base directory. Why: the file would inherit default permissions/temporary-file permissions rather than enforced `0600`, carries user workflow metadata (`activeModeID`, custom recipes, processor/capture/output-sink config), is not app-layer encrypted, and has no expiry or delete path beyond overwrite-on-save; if the store becomes live, base-directory migration would strand it in the old location. I did not find a production instantiation of `WorkflowModeStore` under `Sources/`, so this currently looks latent rather than active. Mitigation: route the write through an explicit-permission atomic writer, or set `0600` after save, and either move the sidecar under a managed subdirectory or teach the migrator to carry root-level files as well.
- low, Sources/PersonalScribeCore/Database/TranscriptRepository.swift:71: Transcript deletion only removes the SQLite row and explicitly leaves any optional on-disk audio sidecars untouched. Why: if raw-audio sidecars are still emitted anywhere else in the app, transcript cleanup is incomplete and the higher-sensitivity audio copy can outlive the row that referenced it; I did not find the creation path in this scoped audit, so this is a documented cleanup gap rather than a fully traced live path. Mitigation: bind audio-sidecar lifecycle to transcript CRUD, or stop writing raw audio to disk if persistence is not strictly required.

## 4. Coverage gaps
- This was a read-only audit. I did not run the app, `swift build`, or `swift test`, so I could not observe the actual runtime SQLite journal mode, the final permissions of created files, or whether macOS/GRDB adds any protections outside the audited code paths.
- The backup/index findings are source-based: the required greps found no exclusions under `Sources/`, but I did not audit launch agents, shell scripts, installer logic, or post-install tooling outside that tree.
- I did not locate a production callsite for `WorkflowModeStore` or `WorkflowModeRegistry`; the `workflow-modes.json` issues are therefore latent unless the store is wired from code outside the searched paths.
- I did not locate the writer for any optional audio sidecar, only the explicit comment that transcript deletion leaves such sidecars behind.
