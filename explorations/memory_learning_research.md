# Memory & Learning System Research for PersonalScribe

Research date: 2026-04-15
Scope: Approaches to learning/memory for local voice dictation WITHOUT model fine-tuning.

---

## 1. Prompt-Based Personalization for Whisper

### How Whisper's `initial_prompt` Works

Whisper's decoder accepts an `initial_prompt` parameter that conditions the output. It was designed to stitch together multi-segment transcriptions by passing the prior segment's text, but it can be repurposed for vocabulary biasing.

**Mechanism:** The prompt text is tokenized and prepended to the decoder's prefill sequence. The decoder then generates text that is stylistically and lexically consistent with the prompt. This is purely lexical bias during decoding -- it does not override acoustic evidence.

**Token limit:** The prompt is capped at **224 tokens** (half of Whisper's 448-token context window). Only the final 224 tokens are used; earlier tokens are silently ignored. Later tokens exert stronger influence.

**Persistence caveat:** The `initial_prompt` only affects the first 30-second segment. After that, Whisper overwrites the prompt with the decoded output of the current segment. whisper.cpp added a `carry_initial_prompt` flag to prepend the initial prompt to every decode window.

### What Works

**Spelling guides** are the most effective zero-shot technique. Embedding proper nouns, product names, and domain terms in the prompt biases transcription toward them:

```
"Glossary: Kubernetes, PostgreSQL, Supabase, WhisperKit"
```

Or in natural sentence form (which some research suggests is slightly more effective):

```
"We discussed the Kubernetes cluster running PostgreSQL and Supabase."
```

**Fictitious transcripts** generated by an LLM can produce longer, more naturalistic prompts that establish style and vocabulary simultaneously. OpenAI's cookbook demonstrates using GPT to generate a fake transcript paragraph containing target vocabulary.

**Multi-pass prompting** (from "Whisper: Courtside Edition," arXiv 2602.18966, Feb 2026): Run Whisper once to get a rough transcript, then use an LLM to analyze it and construct a targeted prompt containing (i) topic/domain context, (ii) canonical proper nouns, (iii) domain jargon. Feed this prompt into a second Whisper pass. This reduced player name errors by ~35% on basketball commentary.

### What Does NOT Work

- **Instructional prompts** ("Please format as markdown", "Use proper capitalization"): Whisper follows stylistic patterns, not imperative instructions.
- **Very short prompts**: Less than ~50 tokens are unreliable at steering output.
- **Acoustic overrides**: A prompt cannot make Whisper hear phonemes that aren't in the audio.
- **Topic-level prompts** without specific vocabulary: A June 2024 paper ("Do Prompts Really Prompt?", arXiv 2406.05806) found that templates guiding Whisper to understand topic information did NOT consistently improve accuracy.

### Benchmark Results

| Study | Domain | Baseline WER | With Prompting | Method |
|-------|--------|-------------|----------------|--------|
| Courtside Edition (2026) | Basketball commentary | 21.7% | ~14% (est.) | Multi-pass LLM-constructed prompt |
| Context injection (MSA) | Arabic dialects | 15.79% | 12.27% | TF-IDF/semantic retrieval prompts |
| KWS-Whisper (2023) | Code-switching | 5.6% MER | 3.6% MER | Keyword spotting + spoken-form prompts |
| B-Whisper prompt-only | English rare words | baseline | 18% R-WER reduction | Prompt with bias words (no fine-tune) |

**Bottom line:** Prompt-only injection yields 15-30% relative improvement for domain terms. Substantial but not transformative. The prompt-only baseline in B-Whisper achieved only 18% rare-word error reduction vs. 45.6% with instruction-tuning.

### WhisperKit Implementation

WhisperKit (argmaxinc/WhisperKit) exposes the prompt mechanism through `DecodingOptions`:

```swift
public var promptTokens: [Int]?   // Token IDs prepended to prefill
public var prefixTokens: [Int]?   // Token IDs appended to prefill
public var usePrefillPrompt: Bool // Force prefill per task/language
```

To use text-based prompts, you must tokenize the string into token IDs first. WhisperKit does not expose a direct `initial_prompt: String` convenience (unlike whisper.cpp's C API which does).

### whisper.cpp Implementation

whisper.cpp provides two approaches:

```c
// Approach 1: String-based (internally tokenized)
params.initial_prompt = "technical terms: Kubernetes, PostgreSQL";

// Approach 2: Pre-tokenized
whisper_token tokens[256];
int n = whisper_tokenize(ctx, prompt_text, tokens, 256);
params.prompt_tokens = tokens;
params.prompt_n_tokens = n;
```

**Known issue:** whisper.cpp's internal tokenizer historically did not perfectly match OpenAI's tiktoken tokenizer (Issue #1098), which could reduce prompt effectiveness. This has been partially addressed in recent versions.

Swift bindings: Available via `whisper.spm` (SPM package) and `SwiftWhisper`.

## 2. Correction Detection Mechanisms

### Approach A: Accessibility API Monitoring (AXUIElement)

macOS provides `AXUIElement` APIs that can read and observe text fields across all applications.

**How it works:**
1. Create a system-wide element: `AXUIElementCreateSystemWide()`
2. Get focused element: `kAXFocusedUIElementAttribute`
3. Read text value: `kAXValueAttribute`
4. Observe changes: Register `AXObserver` for `AXValueChanged` and `AXSelectedTextChanged` notifications

**Detection flow for corrections:**
1. After PersonalScribe pastes transcribed text, record the pasted text and its location
2. Register an `AXValueChanged` observer on the target text field
3. When a change fires, read the new text value
4. Compute diff between original transcription and current text
5. Extract corrections (substitutions, insertions, deletions)

**What Superwhisper does:** Captures three types of context via Accessibility API:
- Selected text (at dictation start)
- Clipboard content (during dictation)
- Application context -- ALL text in the active input field, including scrolled-away content

Super Mode is the only built-in mode with all three enabled by default. This gives rich post-paste context for correction detection.

**Limitations:**
- Requires Accessibility permission (System Preferences > Privacy & Security)
- Cannot be used in sandboxed Mac App Store apps
- Electron apps have known bugs with text selection ranges (Issue electron/electron#36337)
- Privacy concern: effectively lets the app read everything in any text field

**Swift libraries:**
- [DFAXUIElement](https://github.com/DevilFinger/DFAXUIElement) -- lightweight Swift wrapper
- [AXorcist](https://github.com/steipete/AXorcist) -- modern chainable API with fuzzy matching

### Approach B: Diff-Based Detection in an In-App Editor

If PersonalScribe has its own text editor, correction detection is straightforward:

1. Store the original transcription as `original_text`
2. On each text change event (NSTextView delegate), capture `current_text`
3. Compute word-level diff using Levenshtein distance or Swift's `CollectionDifference`
4. Classify changes as:
   - **Substitution**: "kubernetees" -> "Kubernetes" (correction of a domain term)
   - **Deletion**: User removed a hallucinated word
   - **Insertion**: User added missing content (less useful for learning)

**Implementation in Swift:**
```swift
// Swift's built-in diff
let diff = current_words.difference(from: original_words)
for change in diff {
    switch change {
    case .remove(let offset, let element, _):
        // Word was removed or replaced
    case .insert(let offset, let element, _):
        // Word was inserted (possibly a replacement)
    }
}
```

**For fuzzy matching of corrections:** Use Levenshtein distance to match removed words to inserted words at nearby positions. If distance is small relative to word length, it's likely a spelling correction rather than a semantic rewrite.

**SymSpell algorithm** (available in Swift) provides O(1) approximate string matching for dictionaries up to millions of entries, far faster than naive Levenshtein over the whole dictionary.

### Approach C: Clipboard Monitoring

Less reliable than A or B, but simpler:

1. After paste, monitor `NSPasteboard` for new copy events
2. If the user copies text that is similar to (but different from) the original transcription, they likely corrected it elsewhere
3. Use string similarity to detect if the clipboard content is a corrected version

**Weakness:** High false-positive rate. Users copy many things unrelated to transcription.

### What Existing Apps Do

| App | Correction Learning | Mechanism |
|-----|-------------------|-----------|
| **Wispr Flow** | Auto-learns from corrections, adds to personal dictionary | Cloud-based; dictionary entries sent to server for recognition improvement. Max 40 manual entries. Corrections applied locally post-transcription. |
| **VoiceInk** | Manual custom dictionary training | User explicitly adds words. Dictionary terms likely passed as whisper.cpp prompt. Open-source (GPL v3). |
| **Superwhisper** | Full accessibility API context reading | Reads all text in active input field. Does NOT appear to have auto-correction-learning. |
| **Descript** | Glossary for uncommon words | User manually adds to "transcription glossary"; improves future recognition of similar-sounding words. |
| **Apple Dictation** | Blue-line ambiguity highlighting | No learning, no adaptation, no custom vocabulary. |

**Key insight from Wispr Flow's docs:** Their dictionary operates on TWO levels:
1. **Vocabulary words** (recognition boost): Sent to the server to improve speech recognition during transcription. Affects the model's decoding.
2. **Misspelling corrections** (post-processing): Applied after transcription locally. Also shared with the server during sessions.

This two-level approach is directly portable to a local implementation:
- Level 1: Inject vocabulary into Whisper's `initial_prompt`
- Level 2: Apply find-and-replace rules on the decoded text

## 3. Embedding-Based Personal Vocabulary

### Option A: all-MiniLM-L6-v2

**Model size:** 22MB weights (977MB with all variants including ONNX/OpenVINO)
**Embedding dimension:** 384
**Performance:** ~14,000 sentences/sec on CPU; STS-B score ~84-85%
**Max input:** 256 word pieces (truncated beyond)

**On Apple Silicon:**
- No published Apple Silicon benchmarks, but the model is small enough to run comfortably on any M-series chip
- ONNX backend (`backend="onnx"`) recommended for CPU-optimized inference
- bfloat16 precision supported for reduced memory
- Batch processing critical for throughput

**Swift integration path:**
- Convert to CoreML using `coremltools`
- Use ONNX Runtime with CoreML execution provider: `ort = { features = ["coreml"] }`
- Or use the Go implementation ([clems4ever/all-minilm-l6-v2-go](https://github.com/clems4ever/all-minilm-l6-v2-go)) via C bridge

**Use case for PersonalScribe:** Embed all dictionary terms. When a transcription contains an unknown word, find the nearest neighbor in the personal vocabulary. If similarity > threshold, suggest or auto-replace.

### Option B: EmbeddingGemma-300M

**Model size:** 308M parameters (Q8 quantized available)
**Performance on Apple Silicon (M1 Max):** 33.5 embeddings/sec at 0.891 nDCG@10 quality
**Languages:** 100+ (highest-ranking text-only multilingual <500M model on MTEB)

**Integration paths:**
- GGUF format via llama.cpp (but known crash issues with Metal on restart/shutdown)
- ONNX Runtime with CoreML execution provider
- Could be converted to CoreML via `coremltools`

**Verdict:** Higher quality than MiniLM but 14x larger and slower. For a personal vocabulary of hundreds to low-thousands of terms, MiniLM is more than sufficient and far more practical.

### Option C: Apple's NLEmbedding (Built-In, Zero Dependencies)

Apple's `NaturalLanguage` framework provides `NLEmbedding` for word and sentence embeddings, already installed on every Mac.

```swift
import NaturalLanguage

// Word embeddings
let embedding = NLEmbedding.wordEmbedding(for: .english)!
let distance = embedding.distance(between: "kubernetes", and: "docker")

// Find nearest neighbors
embedding.enumerateNeighbors(for: "kubernetes", maximumCount: 5) { neighbor, distance in
    print("\(neighbor): \(distance)")
    return true
}
```

**Embedding dimension:** 512 doubles per word
**Languages:** English, French, and others (not all languages supported)
**No model download needed** -- ships with macOS

**For sentence embeddings:**
```swift
let sentenceEmbedding = NLEmbedding.sentenceEmbedding(for: .english)
```

**Limitations:**
- Vocabulary is fixed to Apple's training corpus -- cannot add custom words
- Quality lower than dedicated sentence transformers for domain-specific tasks
- Language coverage gaps

### Option D: SimilaritySearchKit (Swift Package)

[SimilaritySearchKit](https://github.com/ZachNagengast/similarity-search-kit) provides:
- On-device text embeddings via CoreML models
- Semantic search with configurable backends
- Support for custom CoreML embedding models
- Automatic index management

### Recommended Approach for PersonalScribe

**Use NLEmbedding as a zero-cost baseline.** It's already on every Mac, requires no model download, and provides reasonable word-level similarity for English.

**For better quality:** Convert all-MiniLM-L6-v2 to CoreML and use it for sentence-level similarity matching when comparing transcription segments against stored corrections.

**Practical architecture:**
1. Store personal vocabulary as `{term: String, embedding: [Float], frequency: Int, source: CorrectionSource}`
2. On new transcription, embed each word/phrase
3. For low-confidence words (from Whisper's log probabilities), find nearest neighbors in personal vocabulary
4. If similarity > 0.85, suggest or auto-replace

## 4. Dictionary-Based Learning Without ML

This is the most practical approach for a v1 implementation and can be surprisingly effective.

### Architecture: Auto-Learning Personal Dictionary

```
┌─────────────────────────────────────────────┐
│              PersonalScribe                  │
│                                              │
│  ┌──────────┐    ┌──────────────────────┐   │
│  │ Whisper   │───>│ Post-Processor       │   │
│  │ (prompt   │    │ (find-replace rules) │   │
│  │  injected)│    └──────────┬───────────┘   │
│  └──────────┘               │                │
│       ▲                     ▼                │
│       │              ┌─────────────┐         │
│  ┌────┴─────┐        │ Output Text │         │
│  │ Prompt    │        └──────┬──────┘         │
│  │ Builder   │               │                │
│  └────┬─────┘               ▼                │
│       │              ┌─────────────┐         │
│       │              │ Correction  │         │
│  ┌────┴─────┐        │ Detector    │         │
│  │ Personal │<───────┤ (diff-based)│         │
│  │Dictionary│        └─────────────┘         │
│  └──────────┘                                │
└─────────────────────────────────────────────┘
```

### Data Model

```swift
struct PersonalDictionaryEntry: Codable {
    let term: String                    // Correct spelling
    var alternatives: [String]          // Common Whisper misspellings
    var frequency: Int                  // Times this term appeared
    var correctionCount: Int            // Times user corrected to this
    var lastUsed: Date
    var context: [String]               // Surrounding words for context
    var source: EntrySource             // .userAdded, .autoLearned, .correctionDetected
    var starred: Bool                   // Higher priority in prompt
}

enum EntrySource: String, Codable {
    case userAdded
    case autoLearned       // Appeared frequently in corrections
    case correctionDetected // Detected via diff after paste
}
```

### Prompt Builder Strategy

Build the Whisper `initial_prompt` dynamically per transcription session:

```swift
func buildPrompt(dictionary: [PersonalDictionaryEntry],
                 recentContext: String?,
                 maxTokens: Int = 200) -> String {

    // 1. Sort by priority: starred > high-frequency > recent
    let sorted = dictionary.sorted { entry1, entry2 in
        if entry1.starred != entry2.starred { return entry1.starred }
        if entry1.frequency != entry2.frequency { return entry1.frequency > entry2.frequency }
        return entry1.lastUsed > entry2.lastUsed
    }

    // 2. Build natural sentence containing top terms
    //    (natural sentences work better than bare word lists)
    let topTerms = sorted.prefix(30).map(\.term)
    var prompt = "Vocabulary: " + topTerms.joined(separator: ", ") + ". "

    // 3. Append recent context if available (e.g., last transcription)
    if let context = recentContext {
        let contextTokens = context.split(separator: " ").suffix(50)
        prompt += contextTokens.joined(separator: " ")
    }

    // 4. Truncate to fit token budget
    // Rough estimate: 1 token ≈ 4 chars for English
    while prompt.count > maxTokens * 4 {
        prompt = String(prompt.dropLast(100))
    }

    return prompt
}
```

### Post-Processing: Find-and-Replace Rules

After Whisper decodes, apply learned replacement rules:

```swift
func postProcess(transcription: String,
                 dictionary: [PersonalDictionaryEntry]) -> String {
    var result = transcription

    for entry in dictionary {
        for alt in entry.alternatives {
            // Case-insensitive replacement
            result = result.replacingOccurrences(
                of: alt,
                with: entry.term,
                options: [.caseInsensitive, .diacriticInsensitive]
            )
        }
    }

    return result
}
```

### Correction Learning Loop

```swift
func detectCorrections(original: String, corrected: String) -> [(wrong: String, right: String)] {
    let origWords = original.split(separator: " ").map(String.init)
    let corrWords = corrected.split(separator: " ").map(String.init)

    var corrections: [(wrong: String, right: String)] = []

    // Use Swift's built-in diff
    let diff = corrWords.difference(from: origWords)

    // Pair removals with nearby insertions
    var removals: [(offset: Int, element: String)] = []
    var insertions: [(offset: Int, element: String)] = []

    for change in diff {
        switch change {
        case .remove(let offset, let element, _):
            removals.append((offset, element))
        case .insert(let offset, let element, _):
            insertions.append((offset, element))
        }
    }

    // Match removals to insertions at similar positions
    for removal in removals {
        if let match = insertions.first(where: { abs($0.offset - removal.offset) <= 2 }) {
            let distance = levenshteinDistance(removal.element, match.element)
            let maxLen = max(removal.element.count, match.element.count)
            // If edit distance is small relative to word length, it's a correction
            if distance <= maxLen / 2 {
                corrections.append((wrong: removal.element, right: match.element))
            }
        }
    }

    return corrections
}
```

### Frequency-Based Prompt Ranking

Track term frequency across sessions to prioritize the most-used vocabulary in the limited prompt window:

- **Decay factor:** Apply time-based decay (e.g., halve frequency every 30 days) so stale terms don't dominate the prompt
- **Correction boost:** Terms learned from corrections get 2x weight
- **Cap at ~30 terms** in the prompt to stay within the 224-token limit while leaving room for context

### State of the Art for Dictionary-Based Approaches

**Wispr Flow** is the commercial state of the art: auto-learns from corrections, manual additions, starred priorities, and team dictionaries. Their approach is two-level (server-side recognition boost + local post-processing rules). Max 40 manual entries, 60-char limit per entry.

**Descript** uses a "transcription glossary" -- user adds uncommon words, and future transcriptions are more likely to recognize similar-sounding words.

**VoiceInk** passes dictionary terms as a whisper.cpp prompt parameter. Open source, so the mechanism is inspectable.

The dictionary-based approach is not cutting-edge ML, but it is the approach that ships in every successful commercial dictation product today.

## 5. Apple Foundation Models for Personalization

### What the API Actually Exposes (WWDC 2025, macOS 26)

The Foundation Models framework provides access to Apple's on-device ~3B parameter LLM (AFMTextV7). Key capabilities:

**Guided Generation:**
- `@Generable` macro on Swift structs/enums for structured output
- `@Guide` macro for constrained decoding (ranges, regex patterns)
- Regex-based string generation (e.g., constrain output to specific prefixes)
- Dynamic schemas for runtime-defined structures
- Guarantees type-safe output -- no parsing needed

```swift
@Generable
struct CorrectedText {
    @Guide(description: "The corrected transcription")
    var text: String

    @Guide(description: "Confidence from 0 to 1", .range(0...1))
    var confidence: Double
}
```

**Tool Calling:**
- Model can autonomously invoke Swift functions
- Can access on-device data (contacts, calendar) for personalization
- Privacy-preserving: all on-device

**Sessions:**
- Conversation context management
- System instructions for session-level configuration

### LoRA Adapters

Apple provides a Python toolkit for training rank-32 LoRA adapters:
- Requires Mac with Apple Silicon and 32GB+ RAM, or Linux GPU
- Adapters are model-version-specific (must retrain on each macOS update)
- Distributed via Background Assets framework (not bundled in app)
- Training is resource-intensive; Apple recommends trying prompt engineering first

**Verdict on LoRA for personal vocabulary:** Impractical for per-user personalization. Adapter training requires significant compute, produces version-locked artifacts, and Apple explicitly recommends against it for simple personalization. LoRA is designed for teaching entirely new skills/domains to the model, not for vocabulary customization.

### How to Use Foundation Models for PersonalScribe

The most promising use is **post-processing correction** rather than vocabulary injection:

```swift
import FoundationModels

let session = LanguageModelSession()

@Generable
struct TranscriptionCorrection {
    var correctedText: String
    var corrections: [SingleCorrection]
}

@Generable
struct SingleCorrection {
    var original: String
    var corrected: String
    var reason: String
}

// Use guided generation for post-transcription cleanup
let prompt = """
Personal vocabulary: \(userDictionary.map(\.term).joined(separator: ", "))

Correct any transcription errors in this text, especially for the vocabulary words above.
Do NOT change meaning, only fix obvious speech-to-text errors.

Transcription: \(rawTranscription)
"""

let result = try await session.respond(to: prompt, generating: TranscriptionCorrection.self)
```

This leverages:
- Guided generation for structured correction output
- On-device processing (no network required)
- Personal vocabulary injection via prompt
- Free inference (no API cost)

### Limitations

- Available only on macOS 26+ / iOS 26+ with Apple Intelligence
- ~3B model has limited reasoning compared to larger models
- Cannot fine-tune per-user without LoRA training
- No direct vocabulary injection at the tokenizer level

## 6. Portable Techniques from Python/Windows

### mariov96/scribe (Python, Windows/Linux)

[scribe](https://github.com/mariov96/scribe) is a 100% local, GPU-accelerated voice dictation tool.

**Architecture:**
- Uses `faster-whisper` (CTranslate2-based, 4x faster than openai/whisper)
- Plugin system with pattern-matching commands
- Voice profile learning (claimed but implementation details not public)
- Conversation memory via "memory_scribe" plugin

**Plugin pattern matching:**
```python
class MyPlugin(BasePlugin):
    name = "my_plugin"
    version = "1.0.0"

    def commands(self):
        return [
            {
                'patterns': ['do something cool'],
                'handler': self.do_something,
                'examples': ['do something cool']
            }
        ]
```

**Portable to Swift:** The pattern-matching command system translates directly. The data directory structure (`analytics/`, `logs/`, `sessions/`) is a good model for local data persistence.

**What's NOT portable:** GPU acceleration via NVIDIA CUDA. On macOS, equivalent acceleration comes from CoreML/Metal via WhisperKit or whisper.cpp with Metal backend.

### OpenWhispr (Python, Cross-Platform)

[OpenWhispr](https://github.com/OpenWhispr/openwhispr) provides:
- Custom dictionary words as "context hints to the speech recognition model"
- Local transcription via Whisper/Parakeet
- BYOK (bring your own key) cloud option

**Dictionary mechanism:** Dictionary words are passed as context hints to the speech model. This is the standard `initial_prompt` injection approach.

### Techniques That Transfer to Swift/macOS

| Technique | Python Implementation | Swift/macOS Equivalent |
|-----------|----------------------|----------------------|
| Prompt injection with vocabulary | `whisper.transcribe(audio, initial_prompt=...)` | `whisper_full_params.initial_prompt` or WhisperKit `promptTokens` |
| faster-whisper (CTranslate2) | `faster_whisper.WhisperModel()` | WhisperKit (CoreML) or whisper.cpp (Metal) |
| Post-transcription find/replace | `str.replace()` over dictionary | `String.replacingOccurrences(of:with:)` |
| Frequency tracking | `collections.Counter`, JSON/SQLite | `UserDefaults`, Core Data, or SQLite |
| Pattern matching commands | regex + dict lookup | Swift regex literals + enum dispatch |
| Diff-based correction | `difflib.SequenceMatcher` | `CollectionDifference` (Swift stdlib) |
| Embedding similarity | `sentence_transformers` | `NLEmbedding` (built-in) or CoreML model |
| Trie for vocabulary lookup | `pygtrie` or custom | Custom Swift Trie (no standard library version) |

### Key Insight: The Effective Stack is Simple

Every successful open-source and commercial voice dictation app uses the same fundamental approach:

1. **Dictionary** of user terms (stored as JSON/SQLite)
2. **Prompt injection** of top terms into Whisper's initial_prompt
3. **Post-processing** find-and-replace for known misspellings
4. **Manual dictionary management** UI for adding/removing terms
5. Optionally: **Accessibility API** for context awareness

No production app relies on embeddings, LoRA, or ML-based correction detection. The complexity is in UX polish, not algorithms.

## 7. Recommended Implementation Plan for PersonalScribe

### Phase 1: Dictionary + Prompt Injection (Immediate Value)

**Effort:** ~1-2 weeks
**Dependencies:** None beyond existing whisper.cpp/WhisperKit integration

1. Create `PersonalDictionary` model (JSON-backed, ~100-500 entries)
2. Build prompt from top-N dictionary terms sorted by frequency + recency
3. Pass prompt via `initial_prompt` (whisper.cpp) or `promptTokens` (WhisperKit)
4. Apply post-processing find-and-replace rules on decoded text
5. Add UI for manual dictionary management (add/remove/star terms)

**Expected improvement:** 15-25% reduction in domain-term errors based on published benchmarks.

### Phase 2: Correction Detection + Auto-Learning

**Effort:** ~2-3 weeks
**Dependencies:** Phase 1

1. In-app editor: Use `NSTextView` delegate to detect changes after transcription
2. Compute word-level diff between original and edited text
3. Use Levenshtein distance to identify spelling corrections vs. semantic rewrites
4. Auto-add corrections to dictionary with `source: .correctionDetected`
5. Track frequency: if a correction occurs 3+ times, it becomes permanent
6. For paste-and-edit: Use Accessibility API to observe `AXValueChanged` on target text fields

### Phase 3: Context-Aware Prompt Building

**Effort:** ~1-2 weeks
**Dependencies:** Phase 2

1. Use Apple's `NLEmbedding` (zero dependency) for word similarity
2. When building the prompt, cluster dictionary terms by topic
3. Use the current application name / recent text as a topic signal
4. Select dictionary terms most relevant to the current context
5. Example: coding in Xcode -> prioritize technical terms; email -> prioritize contact names

### Phase 4: Apple Foundation Models Post-Processing (macOS 26+)

**Effort:** ~1-2 weeks
**Dependencies:** macOS 26 availability

1. Use guided generation for structured correction suggestions
2. Pass personal dictionary as context in the LLM prompt
3. Use the on-device model for intelligent correction of ambiguous words
4. Track which corrections are accepted to improve future suggestions

### What NOT to Build

- **LoRA adapters per user:** Training cost too high, version-locked to OS updates
- **Custom embedding model:** NLEmbedding is sufficient for vocabulary matching
- **ML-based correction classifier:** Levenshtein + frequency tracking achieves 90% of the value at 1% of the complexity
- **TCPGen / B-Whisper architectural changes:** These require modifying Whisper's decoder; impractical for a native app using WhisperKit or whisper.cpp
